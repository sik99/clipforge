# ClipForge project brief

## Confirmed goals and constraints

ClipForge is a video-conversion server with a minimalist web client. Its primary purpose is practical experience with distributed system architecture, horizontal scaling, deployment, infrastructure, operations, observability, and debugging, supporting progression toward a Software Architect role. Application coding is secondary and can be delegated to agents.

- The server uses organized plain ASP.NET Core Minimal APIs. The owner confirmed this after comparing endpoint frameworks: v1 has few endpoints, so FastEndpoints' additional conventions and integrated conveniences are not expected to provide enough benefit to justify adopting it. FastEndpoints, Carter, and controllers are outside the selected v1 approach. Exact handler organization remains for later design; this does not select the monolith's internal modules. See [endpoint implementation options and rationale](design-notes.md#endpoint-implementation-options). Use .NET 10 capabilities as the provisional design reference and choose the actual runtime at implementation setup, considering .NET 11 if its release status and toolchain compatibility make it suitable. Revisit earlier if a design or tooling choice requires version-specific functionality. This does not require supporting both runtimes.
- FFmpeg is the selected conversion engine. Invoke an independently installed executable for local v1; a redistributable GPL-enabled CLI build is permitted. The concrete build/version and installation method remain deferred to environment setup. Encoder directions and all third-party software obligations are maintained in the [dependency licensing guide](dependency-licensing.md).
- Publish original ClipForge code under MIT in a public GitHub repository. Actual publication and future Docker/image distribution procedures remain deferred; public source and build instructions do not by themselves require publishing a prebuilt image. See the [licensing guide](dependency-licensing.md#public-source-repositories-build-recipes-and-private-images).
- The first server version will be a modular monolith. Its internal module design will follow decisions about technology, the external API, and the end-to-end workflow.
- For normal local v1 execution, one ASP.NET Core application host serves both the built browser frontend files and the Minimal API from the same origin. A separate frontend-serving process is not required for running the built application. Exact frontend build/publish integration remains open; a separate development server is still a tooling candidate rather than a selected requirement.
- V1 will run on the owner's computer in the Czech Republic and be accessible only from that machine. Access from other machines is deferred until a requirement calls for it. Travel and changes of execution country require considering the territorial patent guidance in the [licensing guide](dependency-licensing.md).
- Store source and converted video files on a persistent local filesystem in v1. No separate media-storage service is selected for this version.
- SQLite is the selected v1 store for job information, including failure information and retained job history. The .NET provider, data-access approach, schema, and concrete versions remain open; apply the [dependency licensing checkpoints](dependency-licensing.md) when selecting the integration and artifacts.
- Design the server API with the future minimal client interaction in mind, including how a user request becomes API calls. Include enough client language/runtime, framework, workflow, and generator design to resolve integration-tooling uncertainty before application implementation. Detailed client UI design and application implementation remain deferred.
- Keep the domain and initial product small. Video conversion provides real functionality for exploring distributed systems and software architecture; expanding media-domain complexity is not a v1 learning goal. Prefer fixed, simple conversion behavior and return design attention to server technology, the external API, and end-to-end workflow before monolith internals. Evolve through user requirements, operational needs, hypotheses, measurements, owner decisions, and verification. A complex distributed deployment is not an initial requirement.
- Consequential system design and infrastructure decisions belong to the owner. See [collaboration rules](agents/collaboration.md) for the decision workflow.
- Use synthetic load; real users are not needed for the learning goals.
- Supported behavior should be production-relevant within its stated limits. A single-node version is acceptable to consider; local resources must not be presented as independent machines.
- Adding replicas with additional per-instance resource budgets is an intentional way to model added nodes, within actual host capacity. Container count alone does not establish added physical capacity or availability.
- Write repository documentation in English. Create directories only alongside meaningful content.

## First-version user flow and scope

- The user selects a local video file through the client, starts the process, and ultimately downloads the converted video to their computer.
- V1 supports two output choices with fixed codec combinations: MP4 with H.264/AVC video and AAC-LC audio, and WebM with VP9 video and Opus audio. The user selects the output format, not individual codecs. Encoder directions are recorded in the [licensing guide](dependency-licensing.md); concrete versions/builds, detailed codec profiles, and quality/settings remain unresolved.
- V1 converts at most one audio track. If the source contains multiple audio tracks, select the first audio track in source stream order, not by language, default flag, or channel count. Encode it as AAC-LC for MP4 output or Opus for WebM output. Do not fall back to another audio track if the selected track fails.
- Conversion succeeds only when video conversion and conversion of the selected audio track, if present, both succeed. V1 has no partial-success outcome or salvage download after failure. If the source has no audio tracks, convert video without audio; successful video conversion is a full success and does not require synthesizing audio.
- V1 omits separate subtitle tracks and provides no subtitle selection, preservation, external subtitle upload, or subtitle-rendering feature. Other advanced media-preservation features are outside v1. Intentional omission of unselected audio or unsupported ancillary content is part of the selected scope, not a partial conversion failure.
- V1 uses best-effort input processing through the selected FFmpeg build. This does not promise conversion of every input the build can recognize. No separately guaranteed input-format set is selected; exact test fixtures, input limits, and detailed handling of unreadable or unsupported media remain open.
- Conversion paths must provide nontrivial processing work, using test inputs that are easy to generate or obtain. Provide two development script files during implementation: one for external media inspection that supplies the required FFprobe arguments, and one for artificial test-video generation with deliberate container/codec combinations. Script interfaces and exact fixture parameters remain open; this requirement does not authorize creating tooling during the current documentation-only phase.
- Retain input media configuration information and the requested output configuration with job information. Derive the stored output configuration from committed conversion settings. Acknowledge upload after accepting the complete stored source and recording readiness for background processing, without waiting for FFprobe. When the background workflow picks up the job, persist its processing state, inspect the source, then attempt conversion. Run FFprobe and FFmpeg outside database transactions. Keep inspection information in memory and persist it with the conversion termination status in one short final transaction, rather than an intermediate inspection commit. Exact input fields, persistence/recovery mechanisms, and internal worker organization remain open. Retaining requested output settings does not require separately inspecting the actual output; such verification is not selected.
- Input metadata inspection is nonblocking: retain usable fields, mark unavailable fields as unknown, and record inspection success, incomplete metadata, or failure with diagnostics. Incomplete inspection information does not create a partial-success job outcome. A missing field or inspection failure does not prevent an otherwise runnable conversion attempt. Do not automatically retry inspection merely because it failed or fields are missing. Restart recovery may repeat inspection when an interrupted cycle never committed its in-memory outcome; the owner accepts losing that information if the server process dies before the final commit. If an independent conversion prerequisite is known to be absent, such as the complete source file, stop and report that failure rather than attempting conversion. Existing conversion-failure policies still apply; do not leave the job paused indefinitely awaiting another inspection attempt. Detailed operational-failure handling and inspection-outcome representation remain open.
- The job-status API exposes requested output configuration as confirmed below. Input inspection metadata remains internal in v1. A standalone public inspection feature is not selected. External development scripts do not require a new product endpoint or UI.
- Retain the observed conversion-termination timestamp for lifecycle information and separate elapsed durations for the inspection and conversion phases for future distributed-system evolution. Persist these with the inspection result and conversion termination status in the short final transaction, for successful and failed conversion outcomes when available. A server-process crash before that commit can lose these measurements; do not invent a conversion-termination timestamp from restart time. Phase durations remain internal in v1; the conversion-termination timestamp is exposed in job status. Exact phase boundaries and representation remain open. This adds job data, not the deferred observability feature or a metrics stack.
- Other video editing or conversion options are deferred until a new user requirement justifies them.
- AV1 and HEVC/H.265 output are possible future extensions, with no selected container/audio combinations or encoder implementations for those extensions. A future version may also add codec selection accompanied by practical client guidance comparing each codec's main attractions and trade-offs. These are candidates beyond v1, not committed later-version features.
- The workflow must support adding output formats and conversion options. Conversion requires the user to commit the required options. Upload completion alone does not authorize conversion.
- V1 submission uses two ordered requests: first create a job with the required conversion options in the request body, committing those options; the server generates and returns the job identifier. Then upload the source video against that existing job using the returned identifier. Upload does not create a job. This replaces the earlier before-or-during-upload commitment flexibility with options-first submission.
- The successful creation response body is a small JSON object containing only the generated job identifier, not the full shared representation used by reads. Expose job IDs in the API as UUID strings. Choose the identifier property name in the later v1 API contract round. UUID version and storage representation remain for technical design. Valid idempotent creation retries return the original identifier; HTTP status, headers, and replay-response details remain for contract specification.
- Successful upload acknowledgment has an empty response body and no polling URI. The client already has the job ID and uses the individual-read operation for polling. Acknowledge acceptance of the complete stored source without waiting for inspection or conversion; exact success status and other headers remain for the method/resource contract.
- The owner retained the two-request sequence after evaluating a combined JSON-and-file multipart submission. Use the acknowledged job ID for upload, status, cancellation, and same-job upload retries; the idempotency key protects creation and recovers the job ID when the creation response is lost. A separate public upload identity or upload-session resource is not required for v1. The upload-only request contains the raw file bytes with `Content-Type: application/octet-stream`, without multipart wrapping or repeated conversion settings. Future byte-offset resumability remains deferred.
- Include the original filename as display metadata in the job-creation request and retain it with job information. Derive the suggested download filename from the original basename and selected output format; v1 has no configurable destination-filename option. Display/download filenames are separate from server-owned storage naming, and the client controls its local save destination. Exact payload field names, filename validation/normalization, and the derived-name pattern remain open.
- The minimal client has one Start button: after file and option selection, it creates the job and then uploads the video automatically. Once upload completes, conversion proceeds without another user action, subject to the single-conversion scheduling constraint.
- Committed conversion options cannot be changed in v1. Reconsider this capability later if it provides useful system-design learning.
- The v1 API will expose manual job cancellation, covering the job's upload and conversion work. The current minimal client will not use this capability. Defer cancellation acknowledgment behavior until implementation complexity is understood. The owner's hybrid candidate is to confirm cancellation immediately for queued work that can be prevented from starting, but acknowledge only the request for running work and expose the final outcome through status, avoiding response latency while waiting for running work to stop. This is not a selected response contract; detailed stopping semantics and restart-recovery interaction remain open.
- Upload begins only after the job has been created with committed options. Defer automatic download versus a user-operated Download button to detailed client design; this interaction choice is not a prerequisite for technology selection. Endpoint paths/methods and payload schemas remain open; raw binary upload encoding is selected. The selected request sequence does not determine the detailed client layout.
- The first minimal client may require the user to keep the page open. Restoring a previous conversion after refreshing or reopening the page is not a required first-client capability.
- While the page is open, the first browser client offers a user-initiated upload retry on the same eligible job. After an uncertain upload response, it checks job status automatically. It continues tracking if the server accepted the complete source and offers retry when the job is eligible for another upload.
- If the first browser client loses the job-creation response before receiving the job ID, it automatically repeats the creation request with the same idempotency key and creation data. The retry cadence, limit, and handling after retries stop remain open.
- After upload completion, accepted conversion work continues even if the client disconnects.
- If a server restart interrupts background processing before the conversion termination outcome is committed, automatically retry the eligible unfinished job after startup, with no lifetime limit on restart-recovery attempts. Discard unconfirmed attempt output instead of trying to reuse it, even if conversion may have finished before the lost commit. Preserve the source until success is durably recorded and expose downloads only after recorded success. Exclude terminal and cancelled jobs from restart retry; stop or rule out a surviving prior FFmpeg process before deleting or replacing its output, and isolate abandoned attempt files from accepted results. If the live worker still knows conversion completed and only persistence failed, try to persist the known outcome before reconverting. V1 has no restart-recovery cooldown/backoff or dead-letter mechanism. Detailed recovery/cleanup mechanisms and persistence-retry behavior remain open; this does not introduce an unlimited live retry loop or automatic retries of ordinary conversion failures.
- For conversion failures unrelated to server restart, stop the affected conversion without automatic retry. Store its failed outcome and a stable machine-readable failure code plus concise human-readable message with the job, and expose that code/message in job status. Failure of either the video or the selected audio track fails the conversion; V1 does not publish a partial result. Put full diagnostic details in logs associated with the job ID. Exact codes, message wording, response schema, and logging technology remain open.
- V1 must accept additional jobs while an earlier conversion is unfinished, but execute only one conversion at a time. Uploads and downloads can proceed independently of sequential conversion execution. Start ready conversion work when the conversion slot is available; do not keep it idle awaiting an earlier-created job that is not ready. Among eligible ready jobs, select the job whose complete upload was accepted and recorded as ready earliest. A conversion recovered after restart keeps its original place in this order. Ready jobs with equal recorded acceptance times may run in any relative order. V1 imposes no application-defined limit on the number of waiting conversions. V1 has no application-defined count limit on simultaneous uploads and downloads across jobs; the existing one-active-upload-per-job rule still applies. Behavior when actual resources are exhausted remains open.
- When the worker is free, select one eligible ready job from SQLite. Query as soon as it is free after a conversion. If a query finds no ready work, wait one second before polling again. V1 uses idle polling alone. Revisit a wake-up signal if the delay when the worker is idle proves noticeable.
- Intentionally allow backlog growth to support later learning about an arrival rate that exceeds conversion capacity. The observability feature, including backlog metrics, dashboards, and alerts, is deferred beyond v1. V1 retains its confirmed job-status, stored failure-information, and diagnostic-logging requirements. Specific future measurements and observability tooling remain unselected; an unlimited application backlog does not imply unlimited memory or storage. Queued jobs do not expire because of time spent waiting.
- Prioritize using available conversion capacity and throughput over preserving submission order. The owner expects to explore multiple workers and parallel conversion in future versions; worker count, extraction/deployment topology, scheduling mechanisms, and the concrete parallelization plan remain unselected. V1 still executes one conversion at a time.
- The API must report a job's current stage in v1; numeric conversion progress is not required. The client learns stage changes by polling job status over HTTP. A small delay before the client learns of a stage change is acceptable. Use a configurable two-second delay after each polling request completes or fails, with at most one request in flight per tracked job. Retry potentially transient read failures at that normal cadence while tracking continues, without immediate retry bursts, exponential backoff, or a transient-failure count cutoff. Keep the last confirmed information as potentially stale; a polling failure does not change the server-side job outcome. Stop polling after a successful read of a terminal outcome or a non-retryable request/contract error. Exact state representation, request timeouts, error mapping, and configuration placement remain for specification. V1 omits server production and client handling of `Retry-After`; revisit when throttling or an explicit server-directed delay is needed.
- Update the server's recorded job state as soon as feasible after the preceding stage finishes, within the constraints of the chosen technology and architecture. This internal update goal does not drive technology selection; no quantitative internal-update latency target is selected.
- Interrupted uploads may restart from the beginning against the same job, preserving its identifier and committed options. Resumable uploads are not required. A transfer interruption does not by itself end the job. Retries are allowed only while no complete source has been accepted and the job remains eligible for upload. A retry can upload changed file contents under the original filename, using the job's committed conversion options. After a server restart, including after a power outage, return a nonterminal job with an interrupted upload and no accepted source to waiting for a retry if its [applicable deadline](#stage-duration-and-transfer-limits) has yet to pass.
- V1 starts otherwise eligible uploads without a minimum free-space threshold. If an upload fails because server storage is full, end that upload attempt without making the job terminally failed. Allow a retry from the beginning against the same job after space is freed, while the job remains eligible under the existing abandonment policy. Use the normal SQLite write to record the observed storage-capacity failure and relevant circumstances with job information. Preserve any saved context if the job later becomes Abandoned. If the full disk also prevents recording the cause and the server restarts before it can be saved, an unknown cause is acceptable in job history. Abandonment records an incomplete submission, not proof that the user deliberately stopped; retained causes must distinguish observed server-capacity problems from voluntary user action. Exact diagnostic fields and API exposure remain open.
- Allow only one active upload per job; an earlier attempt must stop before a retry begins. Partial data and cleanup from different attempts must not interfere. Reject replacing an accepted source, and do not reopen a cancelled or abandoned job through a retry. After an uncertain upload response, the client checks job status before retransmitting. Coordination mechanisms and attempt diagnostics remain open. The abandonment policy is specified below.
- Once an interrupted upload attempt has stopped, an eligible retry can begin while its partial file awaits periodic cleanup. The owner accepts the risk that those retained bytes can cause the retry to run out of disk space. The existing storage-capacity failure policy applies. The partial-file cleanup interval and safe deletion mechanism remain open. After restart, the [background cleanup policy](#converted-result-retention) applies.
- Shared access to conversions and results among trusted callers is acceptable in v1; per-user isolation is not required. Access is limited to the owner's computer, and the v1 API allows access without credentials; application-level authentication is not required. Revisit access policy before enabling access from other machines.

## Converted-result retention

- Retention is configurable, with a default of seven days starting when the successful result becomes available.
- Repeated downloads are allowed and do not extend retention.
- Interrupted result downloads restart from the beginning in v1; download resumption is not required. Retry downloads use the existing converted result while it remains available and do not rerun conversion or extend retention. A failed download does not change the conversion outcome.
- The expiration deadline survives server restarts and is exposed through the API.
- Expiration ends availability for new downloads; physical file cleanup is separate and may follow later.
- Prefer allowing a download already in progress at expiration to finish. This is a tentative preference, conditional on implementation and code complexity; decide later when the expected implementation is clearer, potentially with a prototype.
- Source/result retention settings take effect at server startup and stay fixed for that server run; changing them requires a restart in v1. Preserve existing recorded deadlines, and use the effective setting when each new retention period begins. A job created earlier can use a new duration if its retention period begins after the restart. Live updates are deferred until the settings inventory, useful values, and operational needs are better understood. This decision does not set reload semantics for every other application setting or retention policy.
- While the v1 server is running, periodic cleanup with a delay of a few minutes is acceptable for expired results and source videos eligible for deletion. After restart, admit uploads as soon as the server can safely determine job eligibility from recovered state. Periodic media-file cleanup runs in the background. The interval, timing of the first pass, and safe deletion mechanism remain open.

## Source-video cleanup

- Once the converted result is available for downloading, the uploaded source becomes eligible for cleanup only if no inspection or conversion failure requires diagnostic retention. An inspection failure still requires diagnostic retention when conversion succeeds; it does not change successful conversion into a failed job. Physical deletion follows the [periodic cleanup policy](#converted-result-retention).
- Sources with an observed inspection or conversion failure share one configurable diagnostic-retention policy, with a default of 60 days and deadlines preserved across server restarts. This includes inspection failure followed by successful conversion or cancellation. Retain the source until diagnostic retention expires or an explicit maintenance cleanup request releases it. For either failure phase, start the diagnostic-retention period when the job's terminal outcome is recorded, even if inspection failed earlier. An earlier inspection failure does not start the countdown while the job is active. Preserve the recorded deadline across restarts; cancellation does not erase the failure context, and only an explicit maintenance release overrides the diagnostic hold before expiry.
- V1 includes a developer/maintenance operation that makes a retained source immediately eligible for cleanup, restricted to already terminal jobs. It persists the changed cleanup eligibility/deadline and logs the operation while preserving job and failure history. It does not require a diagnosed, analysed, or fixed state and does not change the job outcome. Explicit release is an exception to automatic diagnostic retention and does not change the global retention setting. Actual file deletion follows safe cleanup; exact routes/methods, environment availability, response contract, and persistence fields remain open.
- On cancellation, a source with no previously observed error or failure becomes immediately eligible for deletion. If an error or failure has already been observed for that job, cancellation preserves the retention/expiration policy applicable to that failure type; it must not erase diagnostic context or override an established retention deadline. This condition is not limited to a terminal conversion failure. Immediate eligibility does not require immediate physical deletion or permit deletion while active work still needs the file. Retention rules for other failure types, partial-file policies, and safe cleanup mechanisms remain open; inspection and conversion failures share the terminal-outcome-based deadline.

## Log retention and stored failure information

- Logs have their own configurable age at which they become eligible for deletion. The owner's tentative default is about 60 days. Choose the exact age, timing reference, rotation, and cleanup granularity after selecting the logging technology and reviewing the retention options it readily supports.
- The concise failure code/message forms part of job information and shares the job's retention policy below. Full diagnostic details, such as FFmpeg output, exception details, and execution context, belong in logs under log retention. V1 requires no separate diagnostic-record store. The existing requirement to retain server-capacity upload-failure context with the job also remains in scope; exact representation of that context is open.
- Defer the persistence schema to the full technical specification and internal design. Job information and retained job history do not imply separate tables. The owner sees a possible common representation for failure code/message and server-capacity upload-failure context, potentially sharing an entry or fields; this is a candidate, not a selected schema. Required retained information and lifecycle behavior must be preserved regardless of representation. Additional detailed diagnosis belongs in logs.
- V1 retains complete job history indefinitely, including failure information, to preserve data for future analytics and statistics. Motivating examples include product evolution and popularity, input/output format usage, and video sizes, potentially informing scaling, worker optimization, extensions, and optimization of popular conversions. These examples are not a finalized metadata schema or an exhaustive list of future questions.
- Analytics and aggregation implementation are deferred beyond v1. Retained fields remain open; defining every future analytical use is not a prerequisite for retaining the history. V1's existing synthetic-load learning scope remains unchanged.
- Configurable job-history expiration is deferred. Evaluate future archival, selective retention, or operator-directed deletion when observed history growth or analytical needs warrant it.

## Stage-duration and transfer limits

- V1 has no application-defined maximum source-file size. This does not imply unlimited host resources or select buffering, hosting request limits, or remaining disk-exhaustion behavior. Align the selected raw-binary upload and hosting settings with the API policy during setup. Revisit an explicit limit if larger or uncontrolled workloads or broader access justify it.
- Conversion has a configurable execution timeout per attempt, separate from queue waiting and HTTP request lifetime. When exceeded, stop the conversion and record failure and diagnostics without automatic retry.
- Choose the conversion-timeout default later, considering the supported workload. Unlimited execution is an explicit candidate for the default, not a selected default.
- Defer the decision on v1 upload/download timeout safeguards until the technology stack is selected and implementation complexity can be assessed. Neither inclusion nor exclusion of these safeguards is selected yet.
- Jobs waiting for an initial upload or retry have a configurable waiting-inactivity timeout defaulting to 24 hours. Start the period at job creation and start a fresh period after an interrupted upload ends, including an upload attempt ended by full server storage. Apply it only while waiting, excluding active transfer, queue waiting, and conversion. Status polling does not extend it, and the recorded waiting deadline survives restarts. A storage-capacity failure does not suspend this policy or allow reopening an abandoned job.
- When restart recovery finds an interrupted upload with no recorded end time, reuse the last saved upload-waiting deadline. Apply the abandonment policy if that deadline has elapsed.
- While a job is waiting for an initial upload or retry, expose its server-calculated abandonment deadline as an absolute timestamp in job status. The client can show the available retry window without reproducing timeout rules or assuming the default duration. This deadline does not limit an active transfer, and the server remains authoritative when admitting an upload. Field naming, timestamp serialization, and representation outside the upload-waiting stage remain open.
- At the waiting deadline, end the job in a terminal Abandoned state. A later submission requires a new job; retain history under the existing job-retention policy. Partial-file cleanup is a separate decision. This waiting timeout does not replace safeguards for active transfers or impose a maximum total job lifetime.
- Queued jobs have no queue-wait timeout or automatic expiration. They remain eligible until processed, failed, or cancelled. This is separate from the confirmed abandonment deadline for jobs awaiting an initial upload or retry, conversion-attempt timeout, and converted-result expiration.

## API contract and compatibility

- The v1 client-server API uses RESTful HTTP, with the two-request job-creation/raw-binary-upload sequence and polling for job status specified above. Detailed endpoint contracts, download response details, and remaining polling details such as request timeouts and exact error classification remain open.
- Application API routes share the lowercase `/api` prefix, distinguishing them from browser-page and frontend-file URLs on the combined host. Exact resource names, remaining route segments, and endpoint methods remain deferred; this does not choose a name for the shared response model or a versioning scheme.
- Finalize property names, nesting, and detailed response schemas in a later v1 API contract round. The current design identifies the data each response includes.
- V1 exposes an endpoint for listing all retained jobs, including active jobs and finished-job history. This permits discovering jobs without already knowing their IDs. It does not require a job-list screen or previous-job restoration in the first minimal client. V1 has no pagination or filtering and returns all retained jobs as a plain JSON array in one response. An empty list returns `[]`. Consider pagination or filtering later if a need emerges. List the most recently created jobs first. The exact endpoint contract remains open.
- The owner confirmed one shared API response model for retrieving a single item and for each item returned by the list operation. Its name is deferred: do not name the individual representation "job status" and the list-item representation "job" as though they were different models. Choose one consistent name later, with workflow/API design and potentially persistence design available as context. This does not select database tables or require an API model to be the persistence entity. The confirmed shared response contents are: job ID and status, original filename, requested output container and video/audio codecs, job-creation time, complete-source acceptance time, observed conversion-termination time, failure code/message when applicable, upload-abandonment deadline while waiting, and current result availability and expiration deadline. No per-job download URL is required; the download operation can use the known job ID. Input inspection details and phase durations remain internal in v1. Use null for unobserved or unreached lifecycle events; exact timestamp names, serialization, nesting, and the detailed state model remain deferred to contract specification. Timestamp terminology must cover failure and termination without implying success. The owner proposed separating workflow step from each terminated step's outcome as a candidate for later evaluation, not a selected enum or persistence schema. The collection returns the same item representation as the individual read.
- Successful retrieval of an existing job's status returns HTTP 200 even when conversion failed; the body contains the job's failed state and failure code/message. An unknown job returns HTTP 404. A server-side inability to retrieve status uses an appropriate 5xx response when a response can be produced. Conversion failure and failure of the status request are separate outcomes. Exact remaining error mappings remain open.
- Request-level HTTP errors use standard Problem Details ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)) in JSON with `application/problem+json`. Specific problem types, application-code extensions, and exact payload details remain open. This does not replace the job-state/code/message representation of conversion failures in successful status responses.
- Job creation requires a client-generated idempotency key in the `Idempotency-Key` HTTP request header, separate from the JSON conversion settings. Reject a missing header with Problem Details before creating a job. Repeating the same creation request with the same valid key returns the same job; a new key represents an intentional new submission. Reusing a valid key with different meaningful creation values, including conversion options or original filename, is rejected with Problem Details. Do not change the original job, silently return it as matching the changed input, or create another job. Compare creation values rather than JSON whitespace or property order. The key is distinct from the server-generated job identifier. Key format and scope, expired-record cleanup, persistence mechanisms, concurrent-retry handling, exact normalization, and the mismatch HTTP status/problem type remain open.
- Creation idempotency survives server restarts while the key remains valid. If a job was durably created before its response was lost, retrying the same key and creation data after restart returns that job. If no job was durably created, a valid retry can create it. Restart alone does not invalidate a key. Detailed persistence/coordination mechanisms remain open.
- For simultaneous identical creation requests using the same valid key, the owner prefers that the later request wait for the first creation to finish and return the same job. This is a tentative preference, conditional on implementation complexity and value; decide during the implementation specification whether to wait or return a temporary in-progress error requiring a later retry. Preventing duplicate job creation remains required either way. Waiting limits, failure handling, and coordination mechanisms remain open.
- Idempotency keys have a configurable fixed creation-retry window, defaulting to 24 hours from successful durable job creation. Retries do not extend it, restarts preserve its deadline, and later job abandonment, failure, conversion completion, or output deletion do not shorten it. This window is independent of job-history retention and upload-waiting abandonment. After expiration, reuse of the same key is treated as a new submission and can create a new job, even with the original creation data. Key expiration does not expire the original job or its job-ID-based operations. Expired-record cleanup and configuration-change semantics remain open.
- Before v1 is published, the server and client may be updated together, including changes that break older development clients. There is no requirement to support older clients against newer servers during this phase.
- Revisit API versioning and compatibility when v1 is finalized and development of the next version begins. No post-v1 compatibility policy is selected.
- The server's public API declarations are the authoritative contract definition; OpenAPI generated from those declarations is the selected specification approach. The OpenAPI version, server-side generator, generation timing and workflow, and agreement checks remain open.
- The owner prefers a build-based workflow that exports OpenAPI from the backend and generates the TypeScript API integration from that file without requiring a separately running normal HTTP server. This is a provisional direction: finalize build-time-versus-runtime generation just before implementation, assessing startup implications with concrete tooling then. Exact tools, build hooks, regeneration frequency, and whether generated files are committed remain open; see [API contract authoring](design-notes.md#api-contract-authoring).
- Provide prepared `.http` request files runnable from the IDE as a fallback for manual API access, including operations absent from the minimal client. The owner tentatively expects occasional manual explorer use. Swagger UI and Scalar remain the shortlist for an embedded browser explorer; Postman and Insomnia are additional standalone-client alternatives under consideration, alongside or instead of an embedded explorer. The owner deferred the final GUI choice until just before implementation. No GUI tool, requirement to embed an explorer, or concrete integration is selected. See the [manual API access notes](design-notes.md#manual-api-access-candidates). Exact examples and IDE compatibility remain for implementation preparation; no request files are created during this documentation-only phase.
- Generated client API integration is the intended, revisitable direction. TypeScript is selected for the client. Defer the frontend framework and client generator selection as a joint decision until other server/API choices have progressed; assess both framework-neutral and framework-aware integration. Reconsider generation if tool support for the required workflows makes it unsuitable; compatibility with schemas, file transfers, errors, and cancellation must be assessed before adopting a concrete toolchain. The UI framework and generators remain unselected.
- Prefer evaluating the server-specification generator and client-code generator together when their criteria are known. A shared toolchain is a candidate for reducing maintenance, not a selected tool or a requirement to use one product.
- OpenAPI-generation timing remains open. Client language/workflow/generator investigation is now part of the design phase to resolve tooling uncertainty. Endpoint calling and HTTP integration tests do not inherently require OpenAPI, although specification-driven tools and checks do.

## Open questions for the requested grilling session

- **Product scope:** input inspection fields and detailed operational-failure handling, encoder implementations and detailed output settings within the minimal media scope. Best-effort input processing, no application-defined maximum source-file size, nonblocking input inspection without automatic inspection retries, retention of input media information and requested output settings, the two output container/codec combinations, the basic local-file-to-downloaded-result flow, and credential-free localhost-only access without per-user isolation are confirmed above. Reference fixtures and development-script interfaces remain open.
- **Lifecycle:** detailed readiness/state representation, persistence, work ownership, duplicate attempts, cancellation semantics, exact failure codes and API schemas, logging technology, and server restart recovery mechanisms, including recognition of interrupted upload attempts. Client-visible failure code/message, full diagnostics in logs, no application-defined waiting-conversion count limit or queue-wait expiration, starting ready work without waiting for earlier-created unready jobs, continued conversion after client disconnection, unlimited restart-recovery retries without cooldown/backoff or a dead-letter mechanism, no automatic retry for other conversion failures, a manual cancellation API unused by the minimal client, acceptance of overlapping jobs, and one conversion at a time with independent uploads and downloads are confirmed above.
- **Files:** input/output durability mechanisms, failed-source cleanup and explicit deletion mechanisms, remaining failure-type retention rules for cancelled sources, cleanup intervals, timing of the first pass after restart, and safe deletion mechanisms for complete and partial media files, active downloads at result expiry, configuration-change semantics for remaining policies, and disk exhaustion behavior. Restarting interrupted uploads from the beginning, the converted-result retention policy, source cleanup eligibility after result availability, the 60-day default failed-source retention policy, and indefinite job-history retention are confirmed above.
- **Interfaces and tests:** remaining client technology and development hosting, API contracts, status delivery, and service specification tests.
- **Operations:** operating environment and deployment tooling within the confirmed single-machine scope, resource budgets, load scenarios, and latency/completion/error targets. The observability feature and its metrics/tooling belong to later-version design; v1's confirmed job-status and failure-diagnostic requirements remain in scope.
- **Evolution:** evidence or requirements that justify another database, object storage, a broker, independently deployed workers, additional replicas, or another service.

The product name is resolved as **ClipForge**. The remaining questions are discussion topics, not ready implementation tickets.
