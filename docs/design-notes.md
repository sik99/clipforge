# Design notes for future decisions

These notes collect technical rationale, agent proposals, and rationale for confirmed owner decisions. Consult the [project brief](project-brief.md) for decision status; proposals are not approved architecture. Evaluate the relevant assumptions during design; implementation remains deferred.

## Conversion engine

FFmpeg is selected for the current file-to-file conversion scope and future format/options extensibility. The comparison considered [HandBrakeCLI](https://handbrake.fr/docs/en/latest/cli/command-line-reference.html), with its encoding presets and narrower output scope, and [GStreamer](https://gstreamer.freedesktop.org/documentation/tutorials/basic/dynamic-pipelines.html), with composable pipelines and additional integration concepts. Both CLI alternatives would still require execution control and diagnostic capture in ClipForge. Encoder implementations, detailed output settings, exact build, installation method, and integration details remain open.

All license-variant decisions, obligations, official sources, functionality limitations, and future installation/distribution checkpoints are maintained in the [dependency licensing guide](dependency-licensing.md).

Output compatibility requires choosing more than an extension: MP4 is a container whose audio/video codecs and encoding settings also affect player support. [Browser media-format documentation](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers#mpeg-4_mp4) distinguishes the container from its supported codecs. [FFmpeg's own documentation](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/ffmpeg.texi) states that unspecified codecs use the output muxer's default encoders; this does not express a target-player compatibility requirement.

Codec identifiers are distinct from encoder implementations: `avc1` identifies AVC/H.264, `av01` identifies AV1, and `vp09` identifies VP9 in MP4 codec strings. `mp4a` alone does not fully identify the audio codec/profile; `mp4a.40.2` specifies AAC-LC. [Codec-string documentation](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/codecs_parameter) defines these mappings. Exact encoding cost depends on encoder, settings, content, and hardware.

The owner selected two v1 output choices: MP4 with H.264/AVC video and AAC-LC audio, and WebM with VP9 video and Opus audio. The supporting rationale is familiar broad playback compatibility for MP4 and a distinct web-oriented output for WebM. [Media-format guidance](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers) describes both as common containers. These codec combinations are fixed within each output choice for v1; detailed codec profiles and encoding settings remain open. Encoder directions and the permitted GPL CLI integration are maintained in the [licensing guide](dependency-licensing.md); concrete build/version selection remains deferred.

The owner selected one audio track at most for v1. When source audio exists, select the first audio track in source stream order and encode it with the selected output profile's audio codec: AAC-LC in MP4 or Opus in WebM. Do not select by language, default flag, or channel count, and do not try another track if the selected one fails. [FFmpeg's stream-selection documentation](https://ffmpeg.org/ffmpeg.html#Stream-selection) distinguishes explicit mapping from its automatic selection rules; the latter do not express the owner's first-audio-track policy.

Video conversion and conversion of the selected audio track must both succeed for the job to succeed. V1 has no partial-success outcome or salvage result. If the source contains no audio tracks, successfully converting video without audio is a full success. Do not synthesize audio. Failed jobs retain source media and diagnostics under the existing failure policies; successful results follow ordinary result retention and source-cleanup policies.

Changing the video codec to HEVC or AV1 in an MP4 container does not itself restrict the file to one audio track. AV1 in WebM likewise retains the container's multiple-track capability; [FFmpeg's WebM muxer](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/matroskaenc.c) accepts AV1 video and Opus audio, and [AOMedia's AV1 binding](https://aomediacodec.github.io/av1-isobmff/) defines AV1 storage in ISO base media tracks. The owner wants both AV1 and HEVC/H.265 retained as possible future output extensions. Their container/audio combinations, encoder implementations, and delivery versions remain unselected; neither adds a v1 output profile.

The owner requires nontrivial conversion paths and readily obtainable or easily generated test inputs. Cross-codec MP4 H.264/AAC to WebM VP9/Opus and the reverse are proposed reference cases that require re-encoding; changing only a container can be stream copy and is not a sufficient processing workload. The owner selected best-effort input processing through the selected FFmpeg build, as recorded in the [project brief](project-brief.md#first-version-user-flow-and-scope). No separately guaranteed input-format set is selected. Exact fixtures and encoding versus stream-copy policy remain open. Check sample playback once encoder/settings selection is concrete. The v1 user chooses MP4 or WebM; individual codec and technical-setting choices are outside scope. No detailed device-compatibility matrix or benchmark execution plan is selected.

### Minimal v1 media scope

The owner wants real conversion functionality as a vehicle for distributed-systems and software-architecture learning. Additional media-domain complexity is not a v1 goal. The fixed output profiles, first-audio-track selection, binary conversion success/failure, and silent-video support define the intended small domain. Best-effort input handling does not promise preservation of every source feature.

V1 omits separate subtitle tracks and does not provide subtitle selection, external subtitle uploads, subtitle rendering, or other advanced media-preservation features. Subtitles already burned into source pixels remain part of the image; no subtitle removal is implied. Additional audio tracks are intentionally omitted, and there is no subtitle-failure or per-track salvage workflow. Such intentional omissions do not turn an otherwise successful conversion into partial success.

Basic valid playback, orientation, geometry, and synchronization still concern output correctness, but should use fixed, bounded behavior rather than grow into separate client features. Detailed output settings remain open within this small scope. Advanced preservation behavior can be reconsidered when a concrete requirement or architecture-learning exercise justifies it; it is not a prerequisite for completing the current server/API/workflow design.

### Inspecting media and preparing test inputs

[FFprobe](https://github.com/FFmpeg/FFmpeg/blob/master/doc/ffprobe.texi) is an FFmpeg-project command-line tool that reports container and per-stream information, including codec identifiers and profiles, with machine-readable JSON output. Its availability in the chosen package remains for setup verification. FFmpeg's [synthetic video and audio sources](https://github.com/FFmpeg/FFmpeg/blob/master/doc/filters.texi), combined with explicit encoder options, can generate repeatable fixtures in the selected codec combinations. Inspect generated media to check its actual streams; successful metadata inspection alone does not prove the entire file decodes or converts correctly. Synthetic fixtures provide a baseline, not coverage of all real-world media variations.

The owner requires two development script files: a media-inspection script that supplies the required FFprobe arguments, and an artificial test-video generation script. These make deliberate test inputs and repeatable inspection available without memorizing commands. Their interfaces, fixture parameters, and implementation remain deferred; no script is created in this documentation-only phase.

The owner also confirmed retention of input media configuration information and requested output configuration with job information. Derive output configuration from committed conversion settings; these describe the requested result, not independently measured output properties. The fields to retain remain open. Input inspection can observe properties such as container, stream codecs, profiles, and resolution; it does not generally recover a complete original encoder command or all original encoder settings.

The owner confirmed server-side FFprobe inspection of the completed uploaded source before conversion, parsing structured output and retaining selected media properties with the job. Upload acknowledgment precedes inspection, which runs when the background workflow picks up the job. Client-provided metadata is not needed for this approach. Inspection does not establish that the complete source will decode successfully. Input inspection details remain internal in v1 under the confirmed job-status response decision. A developer-facing operation, a standalone public inspection feature, actual-output inspection, and a metadata schema remain unselected.

Inspection and conversion are sequential operations within one background workflow, not one long database transaction. The owner selected a short initial transaction to persist processing state, external inspection and conversion without an open database transaction, and a short final transaction to store the inspection outcome together with the conversion termination status. External processes and filesystem work are not made atomically reversible by a database rollback. Detailed persistence, publication, and recovery coordination remain for the technical specification; the workflow does not dictate internal module or class boundaries.

Persisting inspection immediately in an intermediate transaction was considered but not selected. It would preserve a checkpoint across a crash during conversion, at the cost of another persistence step. The owner instead chose to keep inspection data in memory until the final outcome commit. Short database transactions remain the selected principle: [SQLite permits only one simultaneous write transaction](https://www.sqlite.org/lang_transaction.html), so no write transaction should span the media subprocesses. Other lifecycle, cancellation, or recovery updates may require additional short commits; the workflow does not fix the total transaction count at two or select a data-access library.

The owner accepts that server-process termination before the final commit loses the in-memory inspection outcome and timing information. Repeated server-process crashes during conversion can therefore prevent inspection information from ever being retained with the job. A normal FFmpeg failure or child-process crash can still be observed by the surviving server, which can store inspection data together with the failed conversion outcome. Restart recovery may repeat inspection if no completed outcome was committed; this is recovery of interrupted processing, not a policy of repeatedly probing a recorded failure or missing fields. Final persistence failure and retry details remain for the technical specification.

The owner confirmed acknowledgment of the completed upload without waiting for inspection, followed by inspection and conversion when the background workflow picks up the job. A successful upload response follows acceptance of the complete stored source and recording its eligibility for background processing, not merely receipt of the last request byte; durable handoff mechanisms remain for the technical specification. Persist the processing state at the beginning of the background job cycle. [ASP.NET Core hosted-service guidance](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0) supports queued work within the web application; no separately deployed service is required by this workflow. Concrete worker classes, persistence schema, and internal module boundaries remain open.

The owner also requires the observed conversion-termination timestamp for lifecycle information and separate inspection-phase and conversion-phase elapsed durations to support later distributed-system evolution. Keep these measurements in memory and commit them with inspection data and the conversion termination status, including failed conversion outcomes when measurements are available. The termination timestamp describes the observed end of conversion, not the later database commit or server restart. If the server dies before committing, timing and inspection data for that interrupted cycle can remain unavailable; do not reconstruct an exact termination timestamp from recovery time. Phase durations remain internal in v1, while the observed conversion-termination timestamp is exposed through job status. Phase boundaries, units/serialization, and clock mechanisms remain open. This requirement concerns retained job information and does not bring the deferred observability feature, dashboards, or metrics infrastructure into v1.

Inspection and conversion remain separate logical steps of the same background workflow, rather than independently scheduled stages. A recorded completed inspection outcome, including an incomplete or failed outcome, does not require reinspection merely because fields are absent. Without a committed outcome, a recovered cycle may inspect again. Metadata is not persisted while a job is queued or conversion is running, and inspection occupies part of the serial processing time. Inspection inside the upload request would delay acknowledgment. A separate background inspection stage could populate metadata earlier and overlap inspection with another job's conversion, but would introduce separate scheduling, handoff, and recovery coordination. Neither alternative is selected for v1. Revisit if early metadata becomes a requirement or measurements show inspection limits throughput. Inspection execution limits and detailed cancellation behavior remain open.

The owner confirmed that input metadata is supplementary rather than a prerequisite for conversion. Retain usable observed fields, mark unavailable fields as unknown, and record whether inspection succeeded, was partial, or failed, together with diagnostics, in the final outcome transaction. A missing field, unrecognized input, or probe failure alone does not prevent an otherwise runnable conversion attempt. If an independent prerequisite is known to be absent, such as the complete source file, do not attempt conversion merely because metadata is optional. Do not automatically retry inspection merely for missing fields or a recorded failed outcome; an interrupted background cycle may inspect again under the confirmed restart-recovery policy. Conversion failures remain governed by the no-automatic-retry policy except for restart recovery. Jobs do not remain paused indefinitely awaiting another inspection attempt. Operational-failure handling details and exact inspection-outcome representation remain open.

Future candidates: add AV1 and HEVC/H.265 output support, and user-facing codec selection with concise practical guidance, including each codec's attractions, compatibility considerations, and trade-offs. The owner values the small comparison-table format for helping users make this choice. These candidates are explicitly deferred beyond v1; they are not approved later-version features or UI designs.

FFmpeg supports the selected containers/codecs and future AV1 through configurable muxers and encoder integrations. Support in the upstream project does not guarantee inclusion in an arbitrary downloaded executable; verify the selected build's enabled features and sample conversions. Encoder candidates, license implications, and artifact evidence are maintained in the [licensing guide](dependency-licensing.md#encoder-candidates-for-the-selected-output-profiles).

## Initial conversion and transfer model

Candidate: one application deployment handles upload/download, job submission/status, conversion, and result access, with responsibilities kept distinct in code. Background conversion may invoke a conversion-engine subprocess. A job-metadata database and a message broker solve different problems; asynchronous work alone does not require a broker.

Asynchronous HTTP streaming can handle concurrent uploads and downloads while conversion runs. Dedicated transfer background services are not required merely for concurrency. The upload request stays open until receipt finishes; its response need not wait for conversion. Reading a live request body must remain within the request lifetime. A background service is a lifecycle abstraction, not necessarily a dedicated thread.

Candidate workflow for the selected local-filesystem storage: receive into temporary storage, finalize the complete input, then make conversion eligible. Stream completed results to clients on request. Completion notification and result transfer are separate concerns. Partial uploads, publication, job recovery, cleanup, and scheduling of sequential conversions still need explicit design.

Streaming avoids holding the entire file in application memory, but active transfers still consume connections, buffers, bandwidth, disk I/O, and CPU. Conversion competes for the same host resources.

HTTP `multipart/form-data` is not S3 multipart upload. The latter coordinates separately uploaded parts, completion, and retries/resumption. The owner accepts restarting interrupted uploads from the beginning in v1; resumability is not required. If a future requirement calls for resumability, evaluate established implementations rather than inventing a protocol.

## Timing of user commitment

The owner selected options-first submission: job creation includes and commits the required conversion options, and returns a server-generated job identifier before the client uploads the video to that existing job. This replaces the earlier before-or-during-upload commitment flexibility. The minimal client offers one Start button after file and option selection and automatically performs the two ordered requests. Upload completion makes the job eligible for conversion without another user action, subject to scheduling.

The choice between automatic download and a user-operated Download button is deferred to detailed client design. Both interactions use the same server capability to retrieve an available result, so this choice is not a prerequisite for technology selection. Binary-transfer contract and generator compatibility remain relevant to tooling selection.

The intended user benefit is avoiding a mandatory return after a potentially long upload solely to authorize an already chosen conversion. The interaction should make the current stage and any remaining need for user action clear. The owner separately decided that committed options cannot be changed in v1; this capability may be reconsidered later if it provides useful system-design learning.

## Client connection and conversion lifetime

The owner decided that accepted conversion work continues after the client disconnects, once upload is complete. The first minimal client may still require the page to remain open and need not restore earlier work after reopening. This separates server processing lifetime from client connection lifetime. Result retention is specified separately below; the client learns job status through HTTP polling.

The owner requires automatic retry after startup when a server restart interrupts background processing before its conversion termination outcome is committed. Recovery needs the uploaded input, committed options, and enough persistent lifecycle information to identify eligible unfinished work. The selected policy discards unconfirmed output and reruns the eligible job; it does not attempt to prove that an existing output completed successfully. The owner confirmed no lifetime limit on restart-recovery attempts. Detailed mechanisms remain open.

The owner confirmed unlimited restart-recovery retries for eligible unfinished work, without cooldown/backoff or a dead-letter mechanism in v1. Ordinary observed conversion failures remain terminal without automatic retry. A three-attempt lifetime limit followed by terminal failure was considered but not selected: repeated power interruptions could exhaust it even for valid input, and interruption count does not establish a conversion defect. The selected policy preserves v1 simplicity and lets work recover after an extended period of unreliable power. A job that genuinely crashes the server can be selected again after each restart and may require investigation; the owner accepts that trade-off. Automatic server restart supervision is not selected. Revisit cooldown or an operator-controlled hold if unattended restart becomes a requirement or repeated crash loops are observed. Those are future candidates, with no selected thresholds, durations, state model, or control endpoints. [Retry guidance](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry) supports choosing budgets and delays according to fault context rather than treating a particular interruption count as proof of permanent failure.

Agent assessment, not measured incident probabilities: prioritize ordinary media-conversion failures and deliberate development restarts in v1. FFmpeg is a separate executable, so a native FFmpeg crash does not directly crash ClipForge through a shared address space. [Windows process documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/about-processes-and-threads) describes process address spaces; this is isolation reasoning, not proof against shared-resource exhaustion or ClipForge bugs. No local power-reliability data or workload evidence establishes whether repeated outages or input-associated whole-server crashes are more likely. The owner confirmed omitting a dead-letter mechanism from v1. Observed conversion failures already become Failed jobs with diagnostics and retained source; restart interruptions alone cannot identify defective input. A future operator-controlled hold for repeatedly interrupted jobs could be represented in the existing job store without introducing a broker, but its behavior and release controls would need design. Revisit if actual repeated job-associated server crashes or unattended restart operation warrant it. A dead-letter queue isolates repeatedly unsuccessful work, as illustrated by [SQS documentation](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html); it does not determine why the worker stopped.

The owner confirmed recovery by discarding output whose successful completion was not committed and rerunning eligible unfinished jobs, even if the prior conversion may actually have finished. Accept repeated conversion work after an uncertain outcome. Retain the source until success is durably recorded and expose downloads only after recorded success. Exclude terminal and cancelled jobs from restart retry, stop or rule out a surviving prior FFmpeg process before touching its output, and isolate abandoned attempts from accepted results. Exact process ownership, cleanup, cancellation races, and publication mechanics remain for the technical specification. Restart retry does not introduce automatic retries of ordinary conversion failures or an unbounded live retry loop. If the worker still knows conversion completed and only persistence failed, try to persist that outcome rather than immediately reconverting; retry limits and handling of prolonged database unavailability remain undecided.

An existing or probe-readable output does not establish that the requested conversion finished: interrupted output may still be readable, and logs are not selected as authoritative completion records. Observe the process outcome during execution and use the agreed output success criteria; [FFmpeg error controls](https://ffmpeg.org/ffmpeg.html) affect error handling, so a zero exit code alone must not be described as proof that every source frame was converted without error. Reusing an uncertain output after restart would need a designed completion protocol, such as publishing a finished artifact or completion record only after successful process exit, with durability and identity checks. That can save repeated work but requires recovery coordination across filesystem state and the database. Merely probing the existing file is not equivalent to such a protocol. A third option is marking uncertain attempts failed for manual resubmission, but that would change the confirmed automatic restart-retry requirement.

Persisting processing state and recovering an uncertain output are separate choices. The owner confirmed recording processing state in a short transaction at the beginning of the background cycle, before inspection and conversion. This records the last known lifecycle stage and distinguishes never-started from interrupted work; it does not prove a worker is still alive or that FFmpeg finished. Treat stale processing state as recoverable after restart under the confirmed discard-and-rerun policy. A single-worker design that overlays live processing state from memory was considered but not selected. Attempt-history tables, leases, and multi-worker coordination remain unselected; a persisted processing state does not close the filesystem/database completion gap.

For other conversion failures, the owner requires stopping the affected conversion without automatic retry, storing the failed outcome and a concise code/message with the job, and exposing that code/message through job status. Full diagnostic context belongs in logs associated with the job ID for later diagnosis and analysis. Failure of the video or selected audio track fails the conversion; v1 has no partial-success result. Exact codes, message wording, API schema, logging technology, and job-history retention mechanisms remain open. This distinguishes failures that have been recorded from conversions interrupted by server restart and eligible for recovery.

The owner requires a manual cancellation operation in the v1 API for a [job](../GLOSSARY.md), which covers upload and conversion. The current minimal client will not use it. The owner's rationale is to expose control over work that the server can otherwise continue or retry independently of the client. Cancellation acknowledgment, stopping semantics, and its interaction with restart recovery remain to be specified; deliberate cancellation and interruption by restart need to be distinguished.

The owner deferred choosing whether the cancellation response means request acceptance or completed stopping until implementation complexity can be assessed. Their hybrid candidate is to confirm completed cancellation for queued work that can be prevented from starting, and return request acceptance for running conversion, with subsequent status reporting its outcome. The motivating concern is cancellation-response latency while running work stops. Exact response codes, intermediate states, queue/start races, and stop behavior remain open; the candidate does not confirm a mixed response contract.

The owner requires accepting additional jobs while an earlier conversion is unfinished, with only one conversion executing at a time in v1. Uploads and downloads can proceed independently of sequential conversion execution. When conversion capacity is available, start a ready job without waiting for an earlier-created job that is not ready. This avoids idle conversion capacity imposed solely by creation order; it does not establish an optimal-throughput result or a strict ordering guarantee among ready jobs. The owner confirmed no application-defined count limit on simultaneous uploads and downloads across jobs in v1. The one-active-upload-per-job rule remains in force, and conversion execution remains limited to one at a time. Framework, operating-system, and physical resource limits still apply; this does not select active-transfer timeouts or a buffering/streaming implementation. Selection among multiple ready jobs and resource-exhaustion behavior remain open.

The owner selected no application-defined limit on the number of waiting conversions in v1 and no expiration based on time spent queued. Queued jobs remain eligible until processed, failed, or cancelled. This supports later experience observing, evaluating, and debugging backlog growth when arrivals exceed processing capacity. The observability feature, including backlog measurements, dashboards, and alerts, is deferred beyond v1; specific metrics, instruments, thresholds, and tooling remain unselected. V1 still includes its confirmed job-status reporting, stored failure information, and diagnostic logging. This is an intentional local learning policy, not a claim of unlimited resource capacity or a recommendation for every future deployment. Concrete exhaustion behavior remains open. The [learning ideas](learning-experiments.md#failures-and-overload) retain candidate experiments without establishing a v1 load profile, measurement feature, or execution plan.

The owner prioritizes throughput and expects to explore multiple workers for parallel conversion in future versions. This is an evolution direction, not selection of a worker service topology or a parallel-conversion implementation for v1. Concrete scheduling, capacity/resource budgets, worker count, extraction timing, and experiment plans remain open. The confirmed single-conversion v1 limit is unchanged.

The owner considers stage reporting sufficient for v1; the API need not provide numeric conversion progress. A small delay in client awareness of a stage change is acceptable. This is separate from updating the server's recorded job state, which should happen as soon as feasible after the preceding stage finishes, within the chosen technology and architecture's actual constraints. The owner explicitly does not want that internal update goal to drive technology selection. The exact stage/status model remains open; no quantitative internal-update latency target is selected.

The owner selected client polling of job status over HTTP for v1. Server push is not selected. The owner confirmed the fixed-delay polling and error policy below, without `Retry-After` support in v1; detailed request timeouts, error mapping, and contract remain open. This selects how the client learns state changes without changing the requirement to update server state promptly.

The owner confirmed waiting for the next ordinary poll after potentially transient read failures. Use a configurable fixed polling delay, defaulting to two seconds after the preceding read completes or fails, with at most one read in flight per tracked job. Network/connection failures, client request timeouts, and potentially recoverable responses such as 408, 500, 502, 503, and 504 use the next poll rather than immediate retries. Keep the last confirmed job information, treating it as stale while reads fail; polling failure is not a recorded job failure and must not create or upload another job. Continue ordinary transient-error polling while the page is tracking the job, without a separate retry burst, exponential backoff, or transient-failure count cutoff in v1. Request timeout values and exact configuration placement remain for specification. Future generated-client/query-library choices must respect the selected policy rather than stack independent retries.

The owner confirmed stopping automatic polling after observing a terminal job outcome or a non-retryable request/contract error, such as an unknown-job 404, invalid-request 400, or unusable response representation. Surface a retrieval/compatibility error rather than marking the job Failed. V1 omits `Retry-After` handling. For future reference, [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3) defines the wait hint, and [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) permits it with 429. Treat 429 as retryable rather than treating every 4xx as permanent. This does not select server rate limiting, require a new error response, or change the independently confirmed server-interruption recovery policy. The selected two-second default is a local starting value, not a standard. [Browser timer guidance](https://developer.mozilla.org/en-US/docs/Web/API/Window/setInterval#ensure_that_execution_duration_is_shorter_than_interval_frequency) explains avoiding queued overlapping polling requests. Exact error classification and user-facing error presentation remain for specification.

The owner confirmed omitting `Retry-After` production and client handling from v1. The local credential-free v1 has no selected rate limiter, maintenance mode, or server-directed polling-delay mechanism; normal fixed-delay retries cover its current requirements. A future overload response could return 503 with `Retry-After: 15`, asking the client to wait 15 seconds instead of the normal two-second delay. This follows [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4), but would need a chosen reason and policy for emitting the hint. The header cannot help while the server is entirely down and unable to return a response. Revisit when throttling, explicit temporary-unavailability handling, or an intermediary introduces the hint. The confirmed fixed polling/error policy remains in force.

## Client-server communication

The owner selected RESTful HTTP for the v1 client-server API, including polling for job status and raw binary upload bodies. Detailed resource and endpoint contracts, download response details, and remaining polling details such as request timeouts and exact error classification remain open. Communication between any future independently deployed services is a separate future decision.

The owner confirmed a v1 endpoint for listing all retained jobs, covering active work and finished-job history rather than requiring callers to already know each job ID. Listing job information does not extend video-file retention or restore expired results. The API capability does not add a job-list screen or restoration requirement to the first minimal client. After evaluating pagination complexity and API alternatives, the owner confirmed no pagination or filtering for v1: return all retained jobs in one response. Pagination or filtering may be added later if a need emerges; neither is a committed future feature. Ordering, list-item fields, and the exact endpoint contract remain open. The existing job-history policy governs availability of records.

The owner is considering GUID job identifiers and asked how they interact with pagination; the identifier format is not yet confirmed. Identifier type does not determine list ordering. A proposed chronological listing orders by immutable creation time and then job ID as a unique tie-breaker. A random GUID need not express chronology to break ties deterministically. Queries must request ordering explicitly; a primary key does not establish API response order. [SQLite SELECT documentation](https://www.sqlite.org/lang_select.html#orderby) describes explicit ordering.

Bounded pagination was proposed to limit response size as retained history grows, but is not selected for v1. Offset and cursor approaches remain possible future alternatives, with no approved method, limits, page-size defaults, continuation fields, or query parameters. [Microsoft's pagination guidance](https://learn.microsoft.com/en-us/ef/core/querying/pagination) explains unique ordering and offset/keyset trade-offs; it does not select EF Core for ClipForge. [Google AIP-158](https://google.aip.dev/158) illustrates client-selectable page sizes bounded by a service maximum and opaque continuation tokens. Revisit the contract only when pagination is needed.

The owner selected two ordered data requests: job creation with conversion options in the request body, followed by video upload identifying the existing job through the server-generated identifier returned by creation. Options are committed through creation; the upload operation does not create a job. The minimal client orchestrates both requests from one Start button. The creation-retry principle is confirmed below; detailed duplicate handling remains open.

The owner confirmed an ID-only creation response: return a small JSON object containing only the generated identifier, rather than the full shared representation used by the individual and collection reads. An illustrative body is `{"id":"..."}`; exact property names and identifier format remain deferred. The next normal client action is uploading against that ID, while filename and requested settings are already known locally. The client can obtain server timestamps, deadlines, and current lifecycle information through the existing individual read when needed. Returning the full representation would provide these immediately and reuse its schema, but is not needed for the current creation-to-upload flow. An ID-only acknowledgment adds a small response schema without creating a differently named version of the shared read model. Valid idempotent retries still return the original job's ID; this does not imply the job remains in its initial stage or change upload-eligibility checks. HTTP status, headers, and replay-response details remain for separate contract decisions.

The owner confirmed successful upload acknowledgment with an empty response body and no polling URI. The client already has the ID from creation, and its planned generated API integration can invoke the individual-read operation with that ID. A returned URI is useful for an explicitly link-driven API or dynamically located status resource, but neither is selected for this fixed local-v1 workflow. After acknowledgment, begin the agreed polling workflow; upload acknowledgment does not assert that inspection or conversion finished. Exact success status and response headers remain for the method/resource contract, rather than assuming every empty upload response must use a particular HTTP status. This does not change the shared model used by individual and collection reads.

The rationale is that a separate empty-job creation request still requires creation to precede data submission, while flexible ordering between upload and commitment does not currently justify a third request. The selected sequence supplies an acknowledged job identity before upload for status and cancellation, while keeping creation and option commitment together. Jobs abandoned before upload are handled by the waiting-inactivity policy under [stage-duration limits](#stage-duration-and-transfer-limits). Endpoint paths/methods, schemas, failure responses, and detailed retry contracts remain to be designed; raw binary upload encoding is selected.

A combined JSON-and-file multipart submission was evaluated for its lower request count and potential lifecycle simplification. The owner retained the two-request sequence because it provides an acknowledged job identity before the large transfer and directly supports upload-time status/cancellation and same-job retry. Separate empty-job creation followed by independent upload and commitment was also considered for its ordering flexibility and is unselected. The owner separately chose raw binary encoding for the upload-only request; buffering versus streaming is a distinct implementation decision. [ASP.NET Core upload guidance](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0) describes relevant mechanisms.

Other unselected combinations included upload creating the job, either data operation creating the job, and client-assigned job identifiers. Returning an identifier only after upload would prevent targeting that job for cancellation during upload without another identification mechanism. Allowing either operation to create the job would require shared-identity and concurrent-creation rules.

An upload-first interaction could overlap upload with option selection, reducing preparation time from approximately U + O to max(U, O) for upload duration U and selection duration O, excluding overhead and source-inspection dependencies. It also risks abandoned transfers. This is not supported by the selected v1 sequence; revisit only if a later requirement justifies it. User-visible selection order alone does not establish when another converter begins transferring data.

The owner agreed that repeating the same creation request with the same valid client-generated key returns the same job, while a new key represents an intentional new submission. The earlier phrase "submission key" referred to this idempotency key, not another identifier or mechanism. The server-generated job identifier identifies the resulting job; the idempotency key identifies the creation intent before that response is available. Reuse of a valid key with changed creation input is rejected as described below. Creation idempotency survives restarts; key format and scope, expired-record cleanup, persistence mechanisms, and concurrent-retry handling remain open. [Stripe's documented idempotency-key behavior](https://docs.stripe.com/api/idempotent_requests) illustrates the pattern, not a dependency or adoption of its detailed policy.

The owner confirmed using "idempotency key" consistently for creation-retry protection and "job ID" for the resulting job. "Submission key" is not a general synonym: [Trellix](https://docs.trellix.com/network-and-platform/docs/submission-status-request), for example, uses it for a server-provided identifier for checking submitted-file status. The owner selected the `Idempotency-Key` HTTP request header for job creation, separate from the JSON conversion settings. This treats retry identity as request metadata while the body describes the conversion. [Stripe](https://docs.stripe.com/api/idempotent_requests) uses this header name, while [PayPal](https://developer.paypal.com/api/rest/reference/idempotency/) uses `PayPal-Request-Id`; these examples support header placement without adopting their full contracts. The owner requires this header for job creation because the endpoint creates a new resource. Reject a request without it using Problem Details before creating a job, so every accepted job-creation request has the selected retry protection. This requirement applies to job creation; it does not establish a blanket policy for future resource-creation endpoints. Key format and the exact missing-header error contract remain open.

The owner confirmed preserving creation idempotency across restarts while the key remains valid. If a job was durably created before the client received its identifier, a retry with the same key and creation data returns that job after restart. If no job was durably created, a valid retry can create it. The rationale is to prevent a retained job from being duplicated merely because a restart discarded its creation identity. Restart alone does not end key validity; the validity/retention policy is a separate decision. This is an API behavior requirement, not a selected table layout, transaction, or recovery algorithm.

The owner selected a configurable fixed retry window, defaulting to 24 hours from successful durable job creation; retries do not extend it, and its deadline survives restart. The window is independent of indefinite job-history retention. The key protects the short creation operation. Upload retries use the acknowledged job ID, so a long upload or conversion does not require extending creation-key validity. Do not tie expiration to job completion, since queued work can wait indefinitely and that lifecycle is separate from creation acknowledgment. Sending a creation response is also not proof that the client received it.

Validity until the earliest of job abandonment, conversion-output deletion, or job failure was considered but not selected. It is not necessarily a longer retry window: early job failure could end protection much sooner than a fixed period. It also ties creation-retry behavior to later lifecycle and physical-cleanup events. In the retained two-request model, the client normally already knows the job ID before uploading or converting, so those later events do not define the window needed to recover the initial creation response. Under the selected fixed window, later job events do not shorten creation-key validity.

Finite retry windows are established practice, with differing durations: [Stripe API v1](https://docs.stripe.com/api/idempotent_requests) permits removal of keys after at least 24 hours, while [Adyen](https://docs.adyen.com/development-resources/api-idempotency/) documents validity of 7–14 days after first submission. These examples do not establish a universal duration or adopt either provider's exact contract. The selected 24-hour default is a local-v1 judgment, not an industry-mandated value. The owner confirmed that reuse after expiration is treated as a new submission and can create a new job, even when the creation data matches the original request. The expired association no longer deduplicates that request; retaining it pending physical cleanup must not extend validity. A newly created job receives its own creation-retry window. Expired-record cleanup, configuration-change semantics, interactions with finite job-history deletion, and API exposure of the deadline remain open. Key expiry does not delete a job, cancel conversion, remove history, or affect upload/status/cancellation through its job ID.

Repeated or racing requests within a valid key's window must not create duplicate jobs for one creation intent. For simultaneous identical creation requests, the owner tentatively prefers that the later request wait for the first creation to finish and return the same job. Finalize this behavior during the implementation specification after assessing complexity and value; returning a temporary in-progress error requiring a later retry remains an alternative. Neither response policy may create duplicate jobs. Waiting limits, handling of an unsuccessful first request, exact response contracts, and coordination mechanisms remain open. This distinguishes retries of one intent from intentional new jobs using the same file; content deduplication is not proposed. The confirmed upload-retry policy is described below, with abandonment timing under [stage-duration limits](#stage-duration-and-transfer-limits). Partial-upload cleanup mechanisms and detailed cancellation races remain open.

The owner confirmed rejection of conflicting creation retries while the key remains valid: the same key with the same meaningful creation input returns the original job; the same key with different creation input is rejected through the selected Problem Details envelope. Do not update the original job, silently return it as though it matched the new request, or create another job. An intentional new submission uses a new key. This avoids concealing a client mismatch or treating a retry as an update. [Stripe](https://docs.stripe.com/api/idempotent_requests) and [Amazon EC2](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html) document rejection when a reused key/token carries changed parameters; their exact error contracts are not adopted. Compare creation values, including conversion options and original filename, rather than JSON whitespace or property order. Exact normalization, HTTP status, problem type, and persistence mechanisms remain open.

A per-job download URL is not required because the download operation can take the known job ID. Exact names, nesting, and routes remain for the API specification. The requested output configuration comes from committed settings, not a probe of actual output. Its audio codec describes the selected profile when audio is present, not proof that a silent source gained an audio track. Retaining container and codec fields makes the fixed output profile self-describing without introducing user-selectable codec combinations.

The owner agreed to expose the observed conversion-termination time for success or failure, distinct from the final database commit time. On success this supplies the requested converted-at information without a duplicate timestamp. Exact names remain open: earlier examples such as `createdAt`, `uploadedAt`, and `conversionFinishedAt` are illustrative rather than a selected schema. Use null for events not yet observed or never reached; do not manufacture a conversion-termination time after a crash. UTC representation remains agent guidance for specification, with exact serialization deferred. Input inspection details and inspection/conversion durations remain stored internally in v1. The list uses the same item representation as the individual read, rather than a separate summary model. Exact collection wrapping remains open.

Do not assign one name such as "job status" to the individual response and another such as "job" to the collection items. Use neutral descriptions of the individual and collection operations until one consistent name is chosen. This concerns API representation naming; the existing glossary term Job still describes the requested work. The shared response model does not decide the number or names of database tables or the internal entity structure. A hypothetical future history screen is not a v1 requirement and must not drive a separate response model; design that screen only when the owner introduces it.

For later timestamp and lifecycle modeling, the owner wants terminology that accommodates failed, cancelled, interrupted, and otherwise terminated work, rather than only successful completion. Distinguish successful acceptance of a complete upload from termination of an unsuccessful upload attempt; the accepted-source timestamp must not silently become a last-attempt-ended timestamp. Likewise distinguish the workflow step, whether it was reached or ended, and its outcome. The owner proposed an internal workflow-step enum plus a separate outcome enum for each ended step as one possible representation. This remains a candidate, not a chosen state machine, enum set, per-step record, or table layout. A failed supplementary inspection may still be followed by successful conversion, so a step outcome must not automatically imply the whole job failed. Evaluate timestamp names and event semantics together with that model during contract and technical specification, including failure, cancellation, upload retries, abandonment before conversion, and restart gaps, while preserving the confirmed response contents and recovery behavior.

It supports the general pattern, not adoption of its complete HTTP, error, state, or infrastructure choices; ClipForge's previously confirmed contracts remain authoritative.

### Client-visible failure information

The owner confirmed returning HTTP 200 when job-status retrieval succeeds even if conversion failed. [HTTP 200 semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.1) concern success of the request, and a GET response represents the resource's state. Conversion failure belongs in the retrieved job's state and code/message, while failure to retrieve that representation uses the appropriate HTTP error response: 404 for an unknown job and an appropriate 5xx for server-side retrieval failure when a response can be produced. This lets clients distinguish a known conversion outcome from an unsuccessful status query and avoids treating every failed conversion as a polling/transport failure. Request errors use the selected Problem Details format described below; exact remaining error mappings remain open.

The owner confirmed including a concise human-readable failure explanation and a stable machine-readable failure code in job status when conversion fails. Retain that code/message with job history. The message helps a user understand the outcome; the code lets clients distinguish known categories without parsing prose. Agent guidance for the still-open code taxonomy is to keep it small, with a generic fallback when the cause cannot be classified confidently. [Microsoft's API guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md#handling-errors) illustrate the code/message distinction; their complete error contract and compatibility rules are not adopted.

Full diagnostic details, including raw FFmpeg output, stack traces, and execution context, belong in logs under their existing retention policy. Here, internal diagnostics means those logs, not a separate diagnostic-record store. The job ID associates the client-visible failure with its detailed logs. Concise job failure information remains after log expiration under the separate job-history retention policy; server-capacity upload-failure context is also retained with the job as already required. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html#section-4) distinguishes interface-facing error details from debugging internals. Retrieving a job that failed conversion and failing to execute the status HTTP request are distinct outcomes. Exact job fields, codes, message wording, and representation outside failed jobs remain open. This decision does not change conversion retry policy or make nonblocking inspection/upload-attempt failures terminal conversion failures.

The owner selected standard Problem Details under [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) for request-level HTTP errors, using JSON with `application/problem+json`. This establishes a common error envelope across API operations rather than an independently invented code/message-only response. Problem types, exact field population, any application-code extensions, and endpoint-specific status mappings remain open for contract design and generator evaluation. The selection does not require embedding a Problem Details document in successful job-status responses or adopting another persistence representation.

### Upload-only request encoding

The owner selected raw file bytes as the upload-only request body with `application/octet-stream`. The job is already identified and its conversion settings are committed, so the operation needs no multipart form fields. Reading the request body directly avoids multipart boundary/part parsing and separates file transfer from form binding. This is a simplicity assessment, not a measured performance advantage. Original-filename metadata is supplied and retained through job creation as described below.

Multipart/form-data is the conventional [HTML form upload encoding](https://www.rfc-editor.org/rfc/rfc7578.html), with browser [FormData](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest_API/Using_FormData_Objects) support and standard per-file name metadata. Raw-body transfer is also established in dedicated file/object APIs, such as [S3 PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html); no overall popularity ranking is inferred. Both are valid for a browser client and both can be streamed. Multipart may offer convenient framework/form binding, but [ASP.NET Core's buffered and streaming approaches](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0) must be distinguished for large files.

[OpenAPI supports both raw binary bodies and multipart binary parts](https://spec.openapis.org/oas/v3.1.1.html#working-with-binary-data). A concrete server generator and TypeScript client generator still need representative workflow checks; neither encoding guarantees correct generated behavior or efficient large-file handling by itself. Raw binary is selected; endpoint methods/paths and generators remain open.

For a raw upload, the job ID can be a URL path parameter independently of the binary body; a route such as `/jobs/{jobId}/source` is illustrative, not selected. The owner confirmed including the original file's display name in job creation, retaining it with job metadata, and deriving a suggested download filename from its basename and the selected output format. V1 has no configurable destination-filename option. Original display names, suggested download names, and server-owned storage paths have separate roles; the server chooses its internal storage naming, and the client controls the local save destination. [Content-Disposition](https://www.rfc-editor.org/rfc/rfc6266.html) can convey the suggested download filename. Payload field names, filename validation/normalization, exact derived-name pattern, endpoint methods, and download-response headers remain unselected.

### Submission alternatives and retained decision

A multipart request can carry structured conversion options and streamed binary content; [OpenAPI describes multipart bodies and per-part encoding](https://spec.openapis.org/oas/v3.1.1.html#encoding-multipart-media-types), and [ASP.NET Core's MultipartReader](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0#upload-large-files-with-streaming) supports reading file sections without whole-file memory buffering. A combined implementation would need evaluation of JSON binding, part-order rules, server metadata generation, and client-generator compatibility. One combined request does not make database and file effects atomic, remove partial-file cleanup, or determine whether conversion runs asynchronously after upload acceptance. Both submission shapes can use streamed transfer and background conversion. The combined alternatives below are unselected; the retained two-request design uses a raw binary upload-only body.

One candidate creates the durable job only after the complete multipart body is accepted. This can remove jobs waiting for an initial upload, but removes the normally acknowledged server-generated job identifier during that upload. Interrupted transfers can discard partial data and restart the combined request. A complete upload followed by a lost response still requires idempotency and outcome recovery to avoid duplicate jobs or conversions. Under the existing manual-cancellation and status requirements, addressing work during upload would need a different client-known correlation/identity mechanism or a scope change. If the server observes an incomplete aborted transfer and creates no job, cancellation can consist of abandoning the upload and cleaning its partial file. However, a client abort can race complete acceptance and job creation, so a lost response or connection abort alone does not prove that no job exists. Do not equate that uncertain outcome with confirmed job cancellation.

Another candidate creates the job when its options part is read, before the file is complete. That retains incomplete-upload lifecycle, abandonment, and retry concerns despite using one submission request. The client normally learns a server-generated identifier only from the eventual response; same-job recovery after interruption would need a discoverable mapping from a client-known key or another deliberately selected identity mechanism. The existing creation idempotency key is a possible starting point for this design, not a selected lookup/retry contract. It does not by itself define how incomplete uploads are replaced, completed uploads are recognized, or racing attempts are serialized.

The owner retained the acknowledged job ID as the handle for status, cancellation, and same-job upload retries. The idempotency key has a different role: recovering one creation intent when its response or job identifier was not received. Long transfer duration does not itself make an idempotency key unsuitable, but retention and concurrent-request behavior must cover the intended transfer/retry period. Using the key to discover an upload or job can be valid if explicitly designed; no separate lookup contract is selected. A separate upload identifier would be an option if an upload had to exist before a job was created, but no separate public upload identity is required for v1. Creating a job at JSON arrival retains substantially the same pre-upload state as the two-request model while delaying the client's normal acknowledgment of the job ID.

Byte-offset resumption is independent of whether the initial submission combines options and bytes. It requires retained partial bytes, a recoverable upload identity, server-reported progress, consistency rules, and subsequent continuation requests. Ordinary multipart/form-data supplies none of those resumption semantics by itself. [The tus protocol](https://tus.io/protocols/resumable-upload) illustrates offset discovery and continuation, and its Creation With Upload extension combines upload-resource creation with initial file bytes. This demonstrates that a separate ClipForge job-creation request is not inherently required for future resumability; it does not make a JSON/file multipart endpoint tus-compatible or select tus for ClipForge. Moving to a resumable protocol would still require additional API and client work under either initial design.

A future job-after-upload design could retain an upload session containing partial bytes, immutable conversion options, and transfer progress, then create the job once upload completes. Continuation would identify the session and accepted offset and send remaining bytes, without resending or changing conversion settings. Session completion must create at most one job, with a recoverable association after an uncertain response. The client must learn the upload identity before interruption or recover it through an explicitly selected mechanism. This moves unfinished-transfer lifecycle and cleanup from jobs into upload sessions rather than eliminating them; no upload-session domain term, endpoint, or resumability feature is selected for v1.

Partial-file cleanup and uncertain upload completion exist under both submission shapes. The two-request model supplies a known owner and status target for that cleanup/recovery; it does not remove the work or the possibility of a lost upload acknowledgment. For a combined job-after-upload operation, a candidate outcome-recovery contract would resolve the client-generated idempotency key to an accepted job, preserve the key-to-job association with creation, and serialize retries/finalization so one intent cannot create duplicate jobs. A missing lookup result is not proof that an earlier request cannot still finish; retry admission and finalization must handle that race. No lookup endpoint or concurrency mechanism is selected.

The current two-request design can instead recover a lost upload response through the known job ID and its recorded source-acceptance state. If accepted, continue status polling rather than resend; if the previous attempt is still active, wait for it to end; if no complete source was accepted and the job is eligible again, restart upload from the beginning. The upload operation must recheck eligibility when acting, because a status response does not reserve the right to retry and can become stale. Source-acceptance representation, recovery coordination, and exact responses remain open.

Future resumability would add retained-byte/offset and consistency information in the two-request model as well. With one source per job, that information could be associated with the job without introducing a separately addressable public upload resource. A chosen resumable protocol or implementation could still use an internal upload session; this is not predetermined by having two requests. The difference is whether the existing job already supplies the identity and lifecycle anchor, not whether resumability requires state.

The owner confirmed retaining the two-request sequence and closing the combined-submission alternative evaluation. The justification is that an acknowledged job identifier before a long transfer directly supports upload-time status/cancellation and retry against the same job, without another public upload identity. Request boundaries are not added solely as a distributed-systems exercise. Partial-file cleanup, uncertain responses, and coordination between media and metadata storage still require handling. Byte-offset resumability and a separate upload resource remain deferred. No existing lifecycle or cancellation requirement is relaxed. Disk-full upload retries follow the policy below.

## Retrying an interrupted upload

The owner confirmed restarting an interrupted transfer from the beginning against the existing job while no complete source has been accepted and the job remains eligible for upload. Preserve its identifier and committed options. A transfer interruption does not by itself end the job. This treats transfer attempts as part of one requested conversion, retaining a stable status/cancellation target and avoiding a new creation request for each interrupted transfer. A new job and new creation idempotency key remain appropriate for a genuinely new submission.

The owner confirmed that full server storage ends the affected upload attempt but leaves the job eligible for retry after space is freed, subject to the existing abandonment deadline and other eligibility rules. Start a fresh waiting period when that attempt ends, as for other interrupted uploads; the default remains 24 hours, survives restarts, and is not suspended because the server lacked capacity. Record the observed capacity failure with job information and preserve it if the job later becomes Abandoned. This separates the job's terminal lifecycle outcome from circumstances contributing to it, avoiding an unsupported inference that abandonment was solely the user's choice. Exact diagnostic representation, client-visible fields, and reliable recording when storage for metadata or logs is also affected remain open. This policy introduces neither automatic upload retry nor a new observability feature.

The agreed boundaries are one active upload per job, with the previous attempt stopped before a retry begins; isolation of partial data and cleanup across attempts; no replacement after a complete source is accepted; and no reopening a cancelled or abandoned job through a retry. After a lost upload acknowledgment, inspect job status before retransmitting. Prevent an old attempt's completion or cleanup from overwriting the current outcome. Implementation mechanisms remain open. Neither byte-offset resumability nor a public upload-attempt resource is required.

The alternative of creating a new job for each interrupted transfer gives every job a simpler upload lifecycle and preserves separate failed-attempt records, but changes the identifier, repeats creation, and means one conversion intent can appear as multiple jobs. Existing-job retries need attempt-level diagnostic information if individual transfer failures must remain observable. Partial-file cleanup timing, attempt diagnostics, source-identity checks, and the complete allowed-state model remain open; abandonment timing is specified under [stage-duration limits](#stage-duration-and-transfer-limits).

## Stage-duration and transfer limits

The owner confirmed no application-defined maximum source-file size for local v1. The rationale is the owner-operated, local-only environment and avoiding an arbitrary cap before representative workload sizes are known. This does not promise unlimited resources. An explicit size limit would provide a predictable per-upload boundary, but would not bound aggregate disk use or storage needed for converted results and temporary files. The owner separately confirmed no application-defined waiting-conversion count limit and retryable disk-full upload failures under the abandonment policy. The owner also confirmed no application-defined concurrent-transfer count limit across jobs. Other resource-exhaustion details remain open. Revisit the size policy when workload evidence or broader caller access warrants it.

No application-defined size limit does not mean that default hosting limits disappear. Review the selected upload path and hosting stack at setup so their effective limits match the agreed API behavior: [Kestrel has request-body limits](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/options?view=aspnetcore-10.0), and [ASP.NET Core upload handling](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0) can introduce form-file limits and buffering. No transfer encoding or implementation mechanism is selected by this recommendation.

The owner accepted a configurable maximum elapsed execution time per conversion attempt, separate from queue waiting and HTTP request lifetime. On timeout, stop conversion execution and record the failure and diagnostics without automatic retry. The default will be chosen later with the supported workload in mind; the owner explicitly wants unlimited execution considered as a possible default. No default is selected.

The owner confirmed a configurable waiting-inactivity timeout with a default of 24 hours for jobs awaiting an initial upload or interrupted-upload retry, ending in a terminal Abandoned state. This distinguishes incomplete submissions from conversion failures for status and history; it does not require a different state for every timeout cause. A later submission requires a new job rather than reopening the abandoned job.

The agreed timing starts the waiting period at job creation and starts a fresh period when an interrupted upload returns the job to waiting. Apply it only while waiting, not while an upload is actively transferring, conversion is queued/running, or a result is available. Polling does not extend the period, and a recorded waiting deadline survives server restarts. The 24-hour default allows an overnight retry window in the local learning environment without leaving forgotten jobs open indefinitely; it is a starting policy rather than an industry-prescribed value. It does not cap total job lifetime or replace active-transfer safeguards. Retain terminal job history under the existing policy; physical cleanup of partial files and exact state representation remain separate decisions.

The owner confirmed exposing the server-calculated abandonment deadline in job status while awaiting an initial upload or retry. Use an absolute timestamp so clients can display a deadline or countdown without duplicating the server's duration, reset, or configuration rules. The deadline is for upload waiting, not active transfer duration; polling does not extend it. A displayed value can become stale, so upload admission still checks authoritative server state. Field naming, wire serialization, and whether the field is absent, null, or historical outside the upload-waiting stage remain open.

The owner deferred the decision on v1 upload/download timeout safeguards until technology-stack selection, so implementation complexity can inform the decision. These safeguards are neither included nor excluded yet. Transfer policies remain agent proposals: distinguish maximum total duration from lack of progress or an unacceptably low transfer rate. Prefer progress/rate safeguards for uploads and downloads, with total-duration caps considered against supported file sizes and expected throughput. A timed-out upload ends that transfer attempt; a timed-out download should not change a successfully converted job into a failed conversion. These active-transfer safeguards are distinct from the confirmed waiting-inactivity policy. The owner selected no queue-wait expiration: waiting for conversion does not abandon a job, while the existing pre-upload abandonment, conversion-attempt timeout, and result-expiration policies remain separate.

Server-side transfer duration can be measured, but completing a server response does not prove the client saved the file. [ASP.NET Core request-timeout middleware](https://learn.microsoft.com/en-us/aspnet/core/performance/timeouts) and [Kestrel transfer-rate controls](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/options?view=aspnetcore-10.0) provide relevant mechanisms; actual enforcement depends on the selected hosting and protocols. Timeout cancellation signals must be handled; terminating the wait for a subprocess does not itself terminate its work. Implementation choices and numeric defaults remain open.

## Measurement and topology limits

For a stored-file flow, measure each bulk-transfer leg: client upload, worker input read, worker output publication, and client download. Also measure queue wait and conversion. Transfer can dominate total turnaround; distinguish result-ready time from time until download completes. Some stages may overlap if formats and processing allow it.

Benchmark job concurrency together with encoder threading: one conversion may already use multiple cores. CPU quotas can cause periodic throttling and affect short-request tail latency. Interpret latency alongside resource usage, throttling, disk/network contention, queue age, completion time, and errors.

Several containers on one host share CPU, memory, storage bandwidth, and a failure domain. Additional replicas model more capacity only within real host headroom. A single-host lab can exercise real protocols but cannot demonstrate independent host failures, disks, or multi-host bandwidth. Record topology and resource budgets alongside results. The owner selected their own computer as the v1 host; deployment tooling and resource budgets remain open. Rented or managed infrastructure, if considered later, would change operator effort, cost, transfer latency, and network dependencies.

## Evolution triggers to evaluate

| Requirement or observed limit | Candidate response for an owner decision |
| --- | --- |
| Large uploads must resume or bypass application compute | Established resumable upload support or direct object-storage uploads; the application may remain a monolith. |
| Processing must execute or recover on other hosts | Independently accessible durable inputs/outputs and explicit artifact references. |
| Conversion resource use, restarts, or deployment disrupts the API | Independently deployed processing with explicit ownership and reliable hand-off. |
| Queue age or completion time misses agreed targets | Compare concurrency, encoder settings, and per-instance capacity before adding worker replicas. |
| Job-state contention, durability, or access requirements exceed the initial database's limits | Reassess persistence and migration; a replacement database is not preselected. |
| Several client-facing APIs need unified routing or shared edge policies | Evaluate a dedicated API gateway. A controller is an application API, not automatically a gateway. |
| Reporting/status queries have distinct load, ownership, or lifecycle needs | Evaluate separating those capabilities; they may remain in the application API. |

Requirements can justify infrastructure before a throughput bottleneck appears. Worker extraction alone does not mandate a gateway or reporting service. This table is a set of discussion triggers, not a service roadmap.
