# Design notes for future decisions

These notes collect technical rationale, agent proposals, and rationale for confirmed owner decisions. Consult the [project brief](project-brief.md) for decision status; proposals are not approved architecture. Evaluate the relevant assumptions during design; implementation remains deferred.

## Conversion engine

FFmpeg is selected for the current file-to-file conversion scope and future format/options extensibility. The comparison considered [HandBrakeCLI](https://handbrake.fr/docs/en/latest/cli/command-line-reference.html), with its encoding presets and narrower output scope, and [GStreamer](https://gstreamer.freedesktop.org/documentation/tutorials/basic/dynamic-pipelines.html), with composable pipelines and additional integration concepts. Both CLI alternatives would still require execution control and diagnostic capture in ClipForge. Encoder implementations, detailed output settings, exact build, installation method, and integration details remain open.

All license-variant decisions, obligations, official sources, functionality limitations, and future installation/distribution checkpoints are maintained in the [dependency licensing guide](dependency-licensing.md).

Output compatibility requires choosing more than an extension: MP4 is a container whose audio/video codecs and encoding settings also affect player support. [Browser media-format documentation](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers#mpeg-4_mp4) distinguishes the container from its supported codecs. [FFmpeg's own documentation](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/ffmpeg.texi) states that unspecified codecs use the output muxer's default encoders; this does not express a target-player compatibility requirement.

Codec identifiers are distinct from encoder implementations: `avc1` identifies AVC/H.264, `av01` identifies AV1, and `vp09` identifies VP9 in MP4 codec strings. `mp4a` alone does not fully identify the audio codec/profile; `mp4a.40.2` specifies AAC-LC. [Codec-string documentation](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/codecs_parameter) defines these mappings. Exact encoding cost depends on encoder, settings, content, and hardware.

The owner selected two v1 output choices: MP4 with H.264/AVC video and AAC-LC audio, and WebM with VP9 video and Opus audio. The supporting rationale is familiar broad playback compatibility for MP4 and a distinct web-oriented output for WebM. [Media-format guidance](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers) describes both as common containers. These codec combinations are fixed within each output choice for v1; detailed codec profiles and encoding settings remain open. Encoder directions and the permitted GPL CLI integration are maintained in the [licensing guide](dependency-licensing.md); concrete build/version selection remains deferred.

The owner selected one audio track at most for v1. When source audio exists, select the first audio track in source stream order and encode it with the selected output profile's audio codec: AAC-LC in MP4 or Opus in WebM. Do not select by language, default flag, or channel count, and do not try another track if the selected one fails. [FFmpeg's stream-selection documentation](https://ffmpeg.org/ffmpeg.html#Stream-selection) distinguishes explicit mapping from its automatic selection rules; the latter do not express the owner's first-audio-track policy.

Video conversion and conversion of the selected audio track must both succeed for the job to succeed. V1 has no partial-success outcome or salvage result. If the source contains no audio tracks, successfully converting video without audio is a full success. Do not synthesize audio. Failed jobs retain source media and diagnostics under the existing failure policies; successful results follow ordinary result retention and source-cleanup policies.

Changing the video codec to HEVC or AV1 in an MP4 container does not itself restrict the file to one audio track. AV1 in WebM likewise retains the container's multiple-track capability; [FFmpeg's WebM muxer](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/matroskaenc.c) accepts AV1 video and Opus audio, and [AOMedia's AV1 binding](https://aomediacodec.github.io/av1-isobmff/) defines AV1 storage in ISO base media tracks. The owner wants both AV1 and HEVC/H.265 retained as possible future output extensions. Their container/audio combinations, encoder implementations, and delivery versions remain unselected; neither adds a v1 output profile.

The owner requires nontrivial conversion paths and readily obtainable or easily generated test inputs. Cross-codec MP4 H.264/AAC to WebM VP9/Opus and the reverse are proposed reference cases that require re-encoding; changing only a container can be stream copy and is not a sufficient processing workload. The owner selected best-effort input processing through the selected FFmpeg build, as recorded in the [project brief](project-brief.md#first-version-user-flow-and-scope). No separately guaranteed input-format set is selected. Exact fixtures and encoding versus stream-copy policy remain open. Check sample playback once encoder/settings selection is concrete. The v1 user chooses MP4 or WebM; individual codec and technical-setting choices are outside scope. No detailed device-compatibility matrix or benchmark execution plan is selected.

### Minimal v1 media scope

The owner wants real conversion functionality as a vehicle for distributed-systems and software-architecture learning. Additional media-domain complexity is not a v1 goal. The fixed output profiles, first-audio-track selection, binary conversion success/failure, and silent-video support define the intended small domain. Best-effort input handling does not promise preservation of every source feature.

V1 omits separate subtitle tracks and does not provide subtitle selection, external subtitle uploads, subtitle rendering, or other advanced media-preservation features. Subtitles already burned into source pixels remain part of the image; no subtitle removal is implied. Additional audio tracks are intentionally omitted, and there is no subtitle-failure or per-track salvage workflow. Such intentional omissions do not turn an otherwise successful conversion into partial success.

Basic valid playback, orientation, geometry, and synchronization still concern output correctness, but should use fixed, bounded behavior rather than grow into separate client features. Detailed output settings remain open within this small scope. Advanced preservation behavior can be reconsidered when a concrete requirement or architecture-learning exercise justifies it; it is not a prerequisite for completing the current server/API/workflow design.

### Inspecting media and preparing test inputs

[FFprobe](https://github.com/FFmpeg/FFmpeg/blob/master/doc/ffprobe.texi) is an FFmpeg-project command-line tool that reports container and per-stream information, including codec identifiers and profiles, with machine-readable JSON output. Its availability in the chosen package remains for setup verification. FFmpeg's [synthetic video and audio sources](https://github.com/FFmpeg/FFmpeg/blob/master/doc/filters.texi), combined with explicit encoder options, can generate repeatable fixtures in the selected codec combinations. Inspect generated media to check its actual streams; successful metadata inspection alone does not prove the entire file decodes or converts correctly. Synthetic fixtures provide a baseline, not coverage of all real-world media variations.

The owner requires two development script files: a media-inspection script that supplies the required FFprobe arguments, and an artificial test-video generation script. These make deliberate test inputs and repeatable inspection available without memorizing commands. Their interfaces, fixture parameters, and implementation remain deferred; no script is created in this documentation-only phase.

The owner also confirmed retention of input media configuration information and requested output configuration with job information. Derive output configuration from committed conversion settings; these describe the requested result, not independently measured output properties. The fields to retain remain open. Input inspection can observe properties such as container, stream codecs, profiles, and resolution; it does not generally recover a complete original encoder command or all original encoder settings.

The owner accepted server-side FFprobe inspection of the completed uploaded source before conversion, parsing structured output and retaining selected media properties with the job. The exact placement relative to upload acknowledgment and queue waiting remains open. Client-provided metadata is not needed for this approach. Inspection does not establish that the complete source will decode successfully. API exposure, a developer-facing operation, a standalone public inspection feature, actual-output inspection, and a metadata schema remain unselected.

Inspection and conversion are sequential operations within one job, not one long database transaction. External processes and filesystem work are not made atomically reversible by a database rollback. Agent proposal: persist relevant outcomes through short database operations, with detailed recovery coordination deferred to internal design. No detailed transaction or recovery mechanism is selected by this explanation.

The owner confirmed that input metadata is supplementary rather than a prerequisite for conversion. Retain usable observed fields, mark unavailable fields as unknown, and record whether inspection succeeded, was partial, or failed, together with diagnostics. A missing field, unrecognized input, or probe failure alone does not prevent an otherwise runnable conversion attempt. If an independent prerequisite is known to be absent, such as the complete source file, do not attempt conversion merely because metadata is optional. Do not automatically retry inspection in v1; proceed to conversion where possible, with conversion failures governed by the existing no-automatic-retry policy except for restart recovery. Jobs do not remain paused indefinitely awaiting another inspection attempt. Operational-failure handling details and exact inspection-outcome representation remain open. The rationale is to preserve best-effort conversion when metadata is incomplete and avoid repeatedly probing unchanged input solely to obtain supplementary information.

Future candidates: add AV1 and HEVC/H.265 output support, and user-facing codec selection with concise practical guidance, including each codec's attractions, compatibility considerations, and trade-offs. The owner values the small comparison-table format for helping users make this choice. These candidates are explicitly deferred beyond v1; they are not approved later-version features or UI designs.

FFmpeg supports the selected containers/codecs and future AV1 through configurable muxers and encoder integrations. Support in the upstream project does not guarantee inclusion in an arbitrary downloaded executable; verify the selected build's enabled features and sample conversions. Encoder candidates, license implications, and artifact evidence are maintained in the [licensing guide](dependency-licensing.md#encoder-candidates-for-the-selected-output-profiles).

## Initial conversion and transfer model

Candidate: one application deployment handles upload/download, job submission/status, conversion, and result access, with responsibilities kept distinct in code. Background conversion may invoke a conversion-engine subprocess. A job-metadata database and a message broker solve different problems; asynchronous work alone does not require a broker.

Asynchronous HTTP streaming can handle concurrent uploads and downloads while conversion runs. Dedicated transfer background services are not required merely for concurrency. The upload request stays open until receipt finishes; its response need not wait for conversion. Reading a live request body must remain within the request lifetime. A background service is a lifecycle abstraction, not necessarily a dedicated thread.

Candidate workflow for the selected local-filesystem storage: receive into temporary storage, finalize the complete input, then make conversion eligible. Stream completed results to clients on request. Completion notification and result transfer are separate concerns. Partial uploads, publication, job recovery, cleanup, and scheduling of sequential conversions still need explicit design.

Streaming avoids holding the entire file in application memory, but active transfers still consume connections, buffers, bandwidth, disk I/O, and CPU. Conversion competes for the same host resources.

HTTP `multipart/form-data` is not S3 multipart upload. The latter coordinates separately uploaded parts, completion, and retries/resumption. The owner accepts restarting interrupted uploads from the beginning in v1; resumability is not required. If a future requirement calls for resumability, evaluate established implementations rather than inventing a protocol.

## Timing of user commitment

The owner selected options-first submission: job creation includes and commits the required conversion options, and returns a server-generated job identifier before the client uploads the video to that existing job. This replaces the earlier before-or-during-upload commitment flexibility. The minimal client offers one Start button after file and option selection and automatically performs the two ordered requests. Upload completion makes the job eligible for conversion without another user action, subject to scheduling.

The choice between automatic download and a user-operated Download button is deferred to detailed client design. Both interactions use the same server capability to retrieve an available result, so this choice is not a prerequisite for technology selection. Binary-transfer contract and generator compatibility remain relevant to tooling selection.

The intended user benefit is avoiding a mandatory return after a potentially long upload solely to authorize an already chosen conversion. The interaction should make the current stage and any remaining need for user action clear. The owner separately decided that committed options cannot be changed in v1; this capability may be reconsidered later if it provides useful system-design learning.

## Client connection and conversion lifetime

The owner decided that accepted conversion work continues after the client disconnects, once upload is complete. The first minimal client may still require the page to remain open and need not restore earlier work after reopening. This separates server processing lifetime from client connection lifetime. Result retention is specified separately below; the client learns job status through HTTP polling.

The owner also requires automatic retry after startup for a conversion interrupted by a server restart. Recovery therefore needs access to the uploaded input, committed options, and enough information to identify the interrupted work across that restart. The storage and recovery mechanisms and restart-related retry limits remain open.

For other conversion failures, the owner requires stopping the affected conversion without automatic retry, storing the failed outcome and relevant circumstances, and logging full diagnostic context for later diagnosis and analysis. Failure of the video or selected audio track fails the conversion; v1 has no partial-success result. A subset of failure information may be made available through the API. The API-visible details, recorded failure fields, logging technology, and job-history retention mechanisms remain open. This distinguishes failures that have been recorded from conversions interrupted by server restart and eligible for recovery.

The owner requires a manual cancellation operation in the v1 API for a [job](../GLOSSARY.md), which covers upload and conversion. The current minimal client will not use it. The owner's rationale is to expose control over work that the server can otherwise continue or retry independently of the client. Cancellation acknowledgment, stopping semantics, and its interaction with restart recovery remain to be specified; deliberate cancellation and interruption by restart need to be distinguished.

The owner deferred choosing whether the cancellation response means request acceptance or completed stopping until implementation complexity can be assessed. Their hybrid candidate is to confirm completed cancellation for queued work that can be prevented from starting, and return request acceptance for running conversion, with subsequent status reporting its outcome. The motivating concern is cancellation-response latency while running work stops. Exact response codes, intermediate states, queue/start races, and stop behavior remain open; the candidate does not confirm a mixed response contract.

The owner requires accepting additional jobs while an earlier conversion is unfinished, with only one conversion executing at a time in v1. Uploads and downloads can proceed independently of sequential conversion execution. When conversion capacity is available, start a ready job without waiting for an earlier-created job that is not ready. This avoids idle conversion capacity imposed solely by creation order; it does not establish an optimal-throughput result or a strict ordering guarantee among ready jobs. Selection among multiple ready jobs, transfer concurrency limits, and resource-exhaustion behavior remain open.

The owner selected no application-defined limit on the number of waiting conversions in v1 and no expiration based on time spent queued. Queued jobs remain eligible until processed, failed, or cancelled. This supports later experience observing, evaluating, and debugging backlog growth when arrivals exceed processing capacity. The observability feature, including backlog measurements, dashboards, and alerts, is deferred beyond v1; specific metrics, instruments, thresholds, and tooling remain unselected. V1 still includes its confirmed job-status reporting, stored failure information, and diagnostic logging. This is an intentional local learning policy, not a claim of unlimited resource capacity or a recommendation for every future deployment. Concrete exhaustion behavior remains open. The [learning ideas](learning-experiments.md#failures-and-overload) retain candidate experiments without establishing a v1 load profile, measurement feature, or execution plan.

The owner prioritizes throughput and expects to explore multiple workers for parallel conversion in future versions. This is an evolution direction, not selection of a worker service topology or a parallel-conversion implementation for v1. Concrete scheduling, capacity/resource budgets, worker count, extraction timing, and experiment plans remain open. The confirmed single-conversion v1 limit is unchanged.

The owner considers stage reporting sufficient for v1; the API need not provide numeric conversion progress. A small delay in client awareness of a stage change is acceptable. This is separate from updating the server's recorded job state, which should happen as soon as feasible after the preceding stage finishes, within the chosen technology and architecture's actual constraints. The owner explicitly does not want that internal update goal to drive technology selection. The exact stage/status model remains open; no quantitative internal-update latency target is selected.

The owner selected client polling of job status over HTTP for v1. Server push is not selected. The polling interval, retry/backoff behavior after failed status requests, and detailed status contract remain open. This selects how the client learns state changes without changing the requirement to update server state promptly.

## Client-server communication

The owner selected RESTful HTTP for the v1 client-server API, including polling for job status and raw binary upload bodies. Detailed resource and endpoint contracts, download response details, and polling policy remain open. Communication between any future independently deployed services is a separate future decision.

The owner selected two ordered data requests: job creation with conversion options in the request body, followed by video upload identifying the existing job through the server-generated identifier returned by creation. Options are committed through creation; the upload operation does not create a job. The minimal client orchestrates both requests from one Start button. The creation-retry principle is confirmed below; detailed duplicate handling remains open.

The rationale is that a separate empty-job creation request still requires creation to precede data submission, while flexible ordering between upload and commitment does not currently justify a third request. The selected sequence supplies an acknowledged job identity before upload for status and cancellation, while keeping creation and option commitment together. Jobs abandoned before upload are handled by the waiting-inactivity policy under [stage-duration limits](#stage-duration-and-transfer-limits). Endpoint paths/methods, schemas, failure responses, and detailed retry contracts remain to be designed; raw binary upload encoding is selected.

A combined JSON-and-file multipart submission was evaluated for its lower request count and potential lifecycle simplification. The owner retained the two-request sequence because it provides an acknowledged job identity before the large transfer and directly supports upload-time status/cancellation and same-job retry. Separate empty-job creation followed by independent upload and commitment was also considered for its ordering flexibility and is unselected. The owner separately chose raw binary encoding for the upload-only request; buffering versus streaming is a distinct implementation decision. [ASP.NET Core upload guidance](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0) describes relevant mechanisms.

Other unselected combinations included upload creating the job, either data operation creating the job, and client-assigned job identifiers. Returning an identifier only after upload would prevent targeting that job for cancellation during upload without another identification mechanism. Allowing either operation to create the job would require shared-identity and concurrent-creation rules.

An upload-first interaction could overlap upload with option selection, reducing preparation time from approximately U + O to max(U, O) for upload duration U and selection duration O, excluding overhead and source-inspection dependencies. It also risks abandoned transfers. This is not supported by the selected v1 sequence; revisit only if a later requirement justifies it. User-visible selection order alone does not establish when another converter begins transferring data.

The owner agreed that repeating the same creation request with the same client-generated key returns the same job, while a new key represents an intentional new submission. The earlier phrase "submission key" referred to this idempotency key, not another identifier or mechanism. The server-generated job identifier identifies the resulting job; the idempotency key identifies the creation intent before that response is available. Key transport, scope, retention, persistence, concurrent retries, and conflicting-payload behavior remain open. [Stripe's documented idempotency-key behavior](https://docs.stripe.com/api/idempotent_requests) illustrates the pattern, not a dependency or adoption of its detailed policy.

The owner confirmed using "idempotency key" consistently for creation-retry protection and "job ID" for the resulting job. "Submission key" is not a general synonym: [Trellix](https://docs.trellix.com/network-and-platform/docs/submission-status-request), for example, uses it for a server-provided identifier for checking submitted-file status. This terminology choice does not select a header name or key format.

Remaining agent duplicate-handling proposals, not yet approved: persist the key-to-job association across restarts and reject reuse with conflicting creation input, including options. Repeated or racing requests must not enqueue duplicate conversion work for the same submission. These proposals distinguish retries of one intent from intentional new jobs using the same file; content deduplication is not proposed. The confirmed upload-retry policy is described below, with abandonment timing under [stage-duration limits](#stage-duration-and-transfer-limits). Partial-upload cleanup mechanisms and detailed cancellation races remain open.

### Upload-only request encoding

The owner selected raw file bytes as the upload-only request body with `application/octet-stream`. The job is already identified and its conversion settings are committed, so the operation needs no multipart form fields. Reading the request body directly avoids multipart boundary/part parsing and separates file transfer from form binding. This is a simplicity assessment, not a measured performance advantage. Original-filename metadata is supplied and retained through job creation as described below.

Multipart/form-data is the conventional [HTML form upload encoding](https://www.rfc-editor.org/rfc/rfc7578.html), with browser [FormData](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest_API/Using_FormData_Objects) support and standard per-file name metadata. Raw-body transfer is also established in dedicated file/object APIs, such as [S3 PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html); no overall popularity ranking is inferred. Both are valid for a browser client and both can be streamed. Multipart may offer convenient framework/form binding, but [ASP.NET Core's buffered and streaming approaches](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0) must be distinguished for large files.

[OpenAPI supports both raw binary bodies and multipart binary parts](https://spec.openapis.org/oas/v3.1.1.html#working-with-binary-data). A concrete server generator and TypeScript client generator still need representative workflow checks; neither encoding guarantees correct generated behavior or efficient large-file handling by itself. Raw binary is selected; endpoint methods/paths and generators remain open.

For a raw upload, the job ID can be a URL path parameter independently of the binary body; a route such as `/jobs/{jobId}/source` is illustrative, not selected. The owner confirmed including the original file's display name in job creation, retaining it with job metadata, and deriving a suggested download filename from its basename and the selected output format. V1 has no configurable destination-filename option. Original display names, suggested download names, and server-owned storage paths have separate roles; the server chooses its internal storage naming, and the client controls the local save destination. [Content-Disposition](https://www.rfc-editor.org/rfc/rfc6266.html) can convey the suggested download filename. Payload field names, filename validation/normalization, exact derived-name pattern, endpoint methods, and download-response headers remain unselected.

### Submission alternatives and retained decision

A multipart request can carry structured conversion options and streamed binary content; [OpenAPI describes multipart bodies and per-part encoding](https://spec.openapis.org/oas/v3.1.1.html#encoding-multipart-media-types), and [ASP.NET Core's MultipartReader](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0#upload-large-files-with-streaming) supports reading file sections without whole-file memory buffering. A combined implementation would need evaluation of JSON binding, part-order rules, server metadata generation, and client-generator compatibility. One combined request does not make database and file effects atomic, remove partial-file cleanup, or determine whether conversion runs asynchronously after upload acceptance. Both submission shapes can use streamed transfer and background conversion. The combined alternatives below are unselected; the retained two-request design uses a raw binary upload-only body.

One candidate creates the durable job only after the complete multipart body is accepted. This can remove jobs waiting for an initial upload, but removes the normally acknowledged server-generated job identifier during that upload. Interrupted transfers can discard partial data and restart the combined request. A complete upload followed by a lost response still requires idempotency and outcome recovery to avoid duplicate jobs or conversions. Under the existing manual-cancellation and status requirements, addressing work during upload would need a different client-known correlation/identity mechanism or a scope change. If the server observes an incomplete aborted transfer and creates no job, cancellation can consist of abandoning the upload and cleaning its partial file. However, a client abort can race complete acceptance and job creation, so a lost response or connection abort alone does not prove that no job exists. Do not equate that uncertain outcome with confirmed job cancellation.

Another candidate creates the job when its options part is read, before the file is complete. That retains incomplete-upload lifecycle, abandonment, and retry concerns despite using one submission request. The client normally learns a server-generated identifier only from the eventual response; same-job recovery after interruption would need a discoverable mapping from a client-known key or another deliberately selected identity mechanism. The existing creation idempotency key is a possible starting point for this design, not a selected lookup/retry contract. It does not by itself define how incomplete uploads are replaced, completed uploads are recognized, or racing attempts are serialized.

The owner retained the acknowledged job ID as the handle for status, cancellation, and same-job upload retries. The idempotency key has a different role: recovering one creation intent when its response or job identifier was not received. Long transfer duration does not itself make an idempotency key unsuitable, but retention and concurrent-request behavior must cover the intended transfer/retry period. Using the key to discover an upload or job can be valid if explicitly designed; no separate lookup contract is selected. A separate upload identifier would be an option if an upload had to exist before a job was created, but no separate public upload identity is required for v1. Creating a job at JSON arrival retains substantially the same pre-upload state as the two-request model while delaying the client's normal acknowledgment of the job ID.

Byte-offset resumption is independent of whether the initial submission combines options and bytes. It requires retained partial bytes, a recoverable upload identity, server-reported progress, consistency rules, and subsequent continuation requests. Ordinary multipart/form-data supplies none of those resumption semantics by itself. [The tus protocol](https://tus.io/protocols/resumable-upload) illustrates offset discovery and continuation, and its Creation With Upload extension combines upload-resource creation with initial file bytes. This demonstrates that a separate ClipForge job-creation request is not inherently required for future resumability; it does not make a JSON/file multipart endpoint tus-compatible or select tus for ClipForge. Moving to a resumable protocol would still require additional API and client work under either initial design.

A future job-after-upload design could retain an upload session containing partial bytes, immutable conversion options, and transfer progress, then create the job once upload completes. Continuation would identify the session and accepted offset and send remaining bytes, without resending or changing conversion settings. Session completion must create at most one job, with a recoverable association after an uncertain response. The client must learn the upload identity before interruption or recover it through an explicitly selected mechanism. This moves unfinished-transfer lifecycle and cleanup from jobs into upload sessions rather than eliminating them; no upload-session domain term, endpoint, or resumability feature is selected for v1.

Partial-file cleanup and uncertain upload completion exist under both submission shapes. The two-request model supplies a known owner and status target for that cleanup/recovery; it does not remove the work or the possibility of a lost upload acknowledgment. For a combined job-after-upload operation, a candidate outcome-recovery contract would resolve the client-generated idempotency key to an accepted job, preserve the key-to-job association with creation, and serialize retries/finalization so one intent cannot create duplicate jobs. A missing lookup result is not proof that an earlier request cannot still finish; retry admission and finalization must handle that race. No lookup endpoint or concurrency mechanism is selected.

The current two-request design can instead recover a lost upload response through the known job ID and its recorded source-acceptance state. If accepted, continue status polling rather than resend; if the previous attempt is still active, wait for it to end; if no complete source was accepted and the job is eligible again, restart upload from the beginning. The upload operation must recheck eligibility when acting, because a status response does not reserve the right to retry and can become stale. Source-acceptance representation, recovery coordination, and exact responses remain open.

Future resumability would add retained-byte/offset and consistency information in the two-request model as well. With one source per job, that information could be associated with the job without introducing a separately addressable public upload resource. A chosen resumable protocol or implementation could still use an internal upload session; this is not predetermined by having two requests. The difference is whether the existing job already supplies the identity and lifecycle anchor, not whether resumability requires state.

The owner confirmed retaining the two-request sequence and closing the combined-submission alternative evaluation. The justification is that an acknowledged job identifier before a long transfer directly supports upload-time status/cancellation and retry against the same job, without another public upload identity. Request boundaries are not added solely as a distributed-systems exercise. Partial-file cleanup, uncertain responses, and coordination between media and metadata storage still require handling. Byte-offset resumability and a separate upload resource remain deferred. No existing lifecycle or cancellation requirement is relaxed. Disk-full upload retries follow the policy below.

## Retrying an interrupted upload

The owner confirmed restarting an interrupted transfer from the beginning against the existing job while no complete source has been accepted and the job remains eligible for upload. Preserve its identifier and committed options. A transfer interruption does not by itself end the job. This treats transfer attempts as part of one requested conversion, retaining a stable status/cancellation target and avoiding a new creation request for each interrupted transfer. A new job and new creation idempotency key remain appropriate for a genuinely new submission.

The owner confirmed that full server storage ends the affected upload attempt but leaves the job eligible for retry after space is freed, subject to the existing abandonment deadline and other eligibility rules. Start a fresh waiting period when that attempt ends, as for other interrupted uploads; the default remains 24 hours, survives restarts, and is not suspended because the server lacked capacity. Record the observed capacity failure with job information and preserve it if the job later becomes Abandoned. This separates the job's terminal lifecycle outcome from circumstances contributing to it, avoiding an unsupported inference that abandonment was solely the user's choice. Exact diagnostic representation, client-visible fields, and reliable recording when storage for metadata or logs is also affected remain open. This policy introduces neither automatic upload retry nor a new observability feature.

The agreed boundaries are one active upload per job, with the previous attempt stopped before a retry begins; isolation of partial data and cleanup across attempts; no replacement after a complete source is accepted; and no reopening a cancelled or abandoned job through a retry. After a lost upload acknowledgment, inspect job status before retransmitting. Prevent an old attempt's completion or cleanup from overwriting the current outcome. Implementation mechanisms remain open. Neither byte-offset resumability nor a public upload-attempt resource is required.

The alternative of creating a new job for each interrupted transfer gives every job a simpler upload lifecycle and preserves separate failed-attempt records, but changes the identifier, repeats creation, and means one conversion intent can appear as multiple jobs. Existing-job retries need attempt-level diagnostic information if individual transfer failures must remain observable. Partial-file cleanup timing, attempt diagnostics, source-identity checks, and the complete allowed-state model remain open; abandonment timing is specified under [stage-duration limits](#stage-duration-and-transfer-limits).

## Minimal-client technology candidates

The owner selected TypeScript with a UI framework rather than plain TypeScript and direct DOM management. Decide the frontend framework and client API generator together, after other server/API decisions have progressed and may have narrowed the candidates. React and Vue remain the framework shortlist; both neutral and framework-aware client generation remain candidates. The client should remain minimal until related functionality provides a worthwhile reason to extend it; distributed backend systems remain the primary learning objective. No UI framework, client generator, or build tool is selected.

The supporting rationale for TypeScript is static checking and potential use with generated API integration. [TypeScript adds a type system to JavaScript](https://www.typescriptlang.org/docs/handbook/typescript-in-5-minutes.html); static types do not validate received JSON at runtime. A small build setup such as [Vite](https://vite.dev/guide/static-deploy.html) remains a candidate, subject to framework/toolchain selection.

The retained comparison is an agent assessment, not an approved framework selection or measured implementation result:

| Candidate | Evaluation |

| [Vue](https://vuejs.org/guide/introduction.html) | A modest simplicity advantage for the current client, with HTML-oriented templates, reactive state, and cohesive official companion tooling. Fully capable of large applications; preferred if minimizing frontend attention is the main criterion. |

## Server endpoint implementation style

The owner selected ASP.NET Core Minimal APIs for v1. [Microsoft's API overview](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/apis?view=aspnetcore-10.0) describes Minimal APIs as direct route-handler declarations and controllers as an alternative using controller classes and actions. Minimal APIs reduce HTTP-layer ceremony and can be organized through route groups and separate registration files. Controllers provide established class/attribute conventions and MVC-specific binding/filter extension points. Both can sit over the same modular-monolith application logic; neither determines job scheduling, persistence, or module boundaries.

Both styles support [OpenAPI generation](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/overview?view=aspnetcore-10.0). Accurate response schemas and endpoint metadata remain necessary in either style. Validation details depend on the selected runtime: [ASP.NET Core 10 introduced built-in Minimal API validation](https://devblogs.microsoft.com/dotnet/announcing-dotnet-10/) enabled through registration, so lack of validation is not an inherent reason to reject Minimal APIs. The runtime version remains open.

The supporting rationale is the current small REST surface without an identified need for MVC-specific extension points. Endpoint organization should remain appropriate to the monolith. The decision concerns HTTP endpoint implementation, not the later internal module design; no throughput advantage is assumed for this workload.

The owner agreed to use capabilities available in .NET 10 as the provisional design reference and finalize the runtime at implementation setup, considering .NET 11 depending on implementation timing, release status, dependency/generator compatibility, and SDK/IDE support. No final runtime version is selected. This does not require supporting both runtimes or multi-targeting. Revisit earlier if a proposed design depends on version-specific functionality or tooling support.

[Microsoft's support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) lists .NET 10 as LTS with support through November 14, 2028, and .NET 11 as an STS release line under the annual release policy. Support duration is distinct from release quality. The major version can affect built-in API/OpenAPI features and compatible packages, but current requirements do not identify a dependency on .NET 11-only functionality. Concrete SDK/runtime patch artifacts and license/provenance evidence belong to setup; no installation is authorized by this discussion.

## API contract authoring

The owner chose OpenAPI as the specification format, generated from the server's public API declarations, making those declarations the authoritative contract definition. Generating the client's API integration from that document is the intended but revisitable direction, subject to client-stack and workflow support. The supporting rationale is the small initial system, coordinated server/client updates before publication, and avoiding a separately hand-maintained specification alongside the implementation. The OpenAPI version, generators, and document-generation timing remain open. ASP.NET Core Minimal APIs are the selected server endpoint implementation approach.

The alternative is a separately authored OpenAPI document as the authoritative contract, with the server implemented against it, optionally using generated server interfaces or stubs. This makes the contract independently reviewable before implementation and can support separately coordinated teams, but requires maintaining the specification and ensuring the implementation follows it. Neither approach automatically verifies all runtime behavior or selects the client-generation tool.

ASP.NET Core supports [OpenAPI generation at runtime and build time](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/aspnetcore-openapi?view=aspnetcore-10.0). Generated documents still depend on accurate [endpoint metadata](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/include-metadata?view=aspnetcore-10.0), particularly for errors and streamed or binary bodies. API declarations should express the intended external contract; generation does not replace designing the workflow or reviewing that contract.

The format comparison also considered [RAML](https://github.com/raml-org/raml-spec/blob/master/versions/raml-10/raml-10.md) and [API Blueprint](https://apiblueprint.org/documentation/specification.html). [TypeSpec](https://typespec.io/docs/emitters/openapi3/openapi/) offers a separate API-authoring language that can emit OpenAPI. The owner selected OpenAPI generated from server API declarations; the standard and authoring direction are settled for v1. Event/message contracts can call for [AsyncAPI](https://www.asyncapi.com/docs); background conversion alone does not establish that requirement.

The owner intends generated client API integration but explicitly wants this direction to remain revisitable until client-language/framework and generator workflow support can be assessed. Resolve the concrete client-stack/generator combination during this design phase, before application implementation, including file transfers, errors, cancellation, and schema support. Actual client-code generation timing remains open. The approach reduces duplicated transport definitions and manual request construction. Regeneration combined with type checking can surface many contract mismatches during development; it does not prove runtime agreement. Generation concerns API integration rather than client UI or workflow orchestration. Language-specific tool selection, generation workflow, and checks remain open.

The owner prefers evaluating server-specification and client-code generators together, potentially using a shared toolchain to reduce maintenance. Generator timing remains open. A shared product is an option, not a requirement or a selected dependency; evaluate overall maintenance and required feature support. [NSwag](https://github.com/RicoSuter/NSwag) illustrates a toolchain that can generate ASP.NET Core OpenAPI descriptions and C#/TypeScript clients, subject to checking the actual selected versions and workflows.

The owner requires reducing tooling uncertainty before finishing design and starting application implementation, and permits any suitable question order to make dependencies easier to resolve. TypeScript is selected. Defer the frontend framework and client API generator as a joint decision until other server/API choices have progressed; those requirements may narrow the candidates. Include both neutral and framework-aware output and consider server specification generation alongside the selection where relevant, then verify representative contract compatibility. No detailed client UI or application implementation is authorized; agree separately on any executable prototype needed for validation.

OpenAPI is useful for specification-driven exploration and contract checks, but is not required to call HTTP endpoints or write ordinary integration tests; [ASP.NET Core integration tests](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests?view=aspnetcore-10.0) can send requests through an HTTP client independently of a specification. A generated document can still support server contract inspection before a client exists. Document-generation timing remains open.

The direction can be selected before a particular client framework: generators can target language and HTTP-runtime libraries, such as OpenAPI Generator's [TypeScript Fetch](https://openapi-generator.tech/docs/generators/typescript-fetch/) and [C#](https://openapi-generator.tech/docs/generators/csharp/) targets. These are evidence of available options, not selected dependencies or guarantees about every target's required features. The compatibility check should use a representative API contract before the concrete toolchain is adopted; evaluate generator, generated-code/runtime dependencies, and licensing under the [dependency licensing guide](dependency-licensing.md).

Candidate reasons to reconsider the authoritative contract definition are independently coordinated client/server teams that need agreement before implementation, external consumers or approval processes requiring a separately governed contract, multiple implementations of the same API, or recurring limitations that make expressing the intended contract in server declarations costly. Publishing v1, requiring compatibility, or distributing the application would not alone require switching to specification-first authoring.

A later switch could begin with the generated OpenAPI document as a reviewed baseline, then make a separately maintained contract authoritative and adapt the existing server to it. Server interfaces or transport types could be generated if suitable tooling supports the required API features. This is a tooling and integration migration with real effort, but it need not change the external API or rewrite conversion behavior. Compatibility policy is separate from contract authoring; contract checks remain necessary in either approach.

## Storage and independent workers

The owner selected a persistent local filesystem for v1 media storage, with no additional media-storage service, and SQLite for job information as described below. This fits the confirmed single-machine scope. Directory layout, durability mechanisms, cleanup, and capacity limits remain open. Host-local paths are not an artifact-access contract for workers on other hosts. Storage migration has costs and may change upload routing and recovery behavior.

Media files and SQLite job information use different persistence representations in v1, potentially on the same physical disk. They are not selected as independent storage services or failure domains, and permanent separation across all future versions is not an established invariant. A single multipart HTTP request would not make arbitrary media-file writes participate in a SQLite transaction; publication, job recording, and recovery still need coordination under either submission shape.

Candidate for a later distributed phase: keep media in durable, independently accessible storage and job state/references in a database. The API can issue scoped, time-limited upload/download authorization; clients then transfer directly to storage. This is an option, not a selected upload path or storage product.

If a queue is introduced, messages can carry job identifiers, media references, and conversion parameters rather than video bytes. Workers need durable inputs accessible for retries on another host. Private local scratch is disposable staging; publish output durably before reporting success. Duplicate attempts and retries must not expose partial or conflicting results. Work ownership and hand-off semantics remain open.

Object APIs use independently addressable objects; path-like keys do not imply filesystem semantics. Remote streaming versus local staging depends on format seekability and workload. Per-host caches or pre-staging add coordination and locality concerns and are optional optimizations.

## Job-metadata persistence

The owner selected [SQLite](https://www.sqlite.org/whentouse.html) for v1 job information. It offers embedded relational storage, transactions, and SQL querying without a separate database service; it allows only one writer at a time per database file. The comparison also considered [LiteDB](https://www.litedb.org/), an embedded .NET document database; ordinary JSON files, which require application design for reliable updates, concurrent access, querying, and schema evolution; and [PostgreSQL](https://www.postgresql.org/docs/current/tutorial-arch.html), a client/server relational database with an additional service to operate.

The supporting rationale is the current single-machine monolith, restart recovery, and retained job history. Write contention should be evaluated against the actual workload. Long retention alone does not establish a need for a separate database server. The .NET provider, persistence access approach, schema, and artifact versions remain open; licensing evidence is maintained in the [dependency licensing guide](dependency-licensing.md).

SQLite was favored over LiteDB for expected regular job metadata and conventional SQL querying of history. This is not based on LiteDB lacking transactions or reporting queries: LiteDB advertises ACID transactions, LINQ, and SQL-like queries. Document storage would become more attractive if the model primarily consisted of variable, nested documents retrieved together. SQLite can also enforce [relationships through foreign keys](https://www.sqlite.org/foreignkeys.html) if the eventual schema needs them; no such schema is selected yet. Current requirements do not establish that LiteDB is unsuitable.

## Converted-result retention

The owner confirmed configurable converted-result retention with a default of seven days. This is an initial setting for the local learning environment that can be adjusted after observing disk use.

The confirmed policy counts retention from when the successful result first becomes available, permits repeated downloads without extending its lifetime, preserves its expiration deadline across server restarts, and exposes the deadline through the API. Retention bounds age rather than total storage usage; capacity limits remain a separate decision. Failed-source cleanup mechanisms, source retention after cancellation, partial-upload cleanup, job-metadata retention, active downloads at expiry, cleanup timing, and the effect of configuration changes remain open.

The owner also confirmed the distinction between expiration and physical cleanup: new downloads are unavailable at expiry, while file cleanup may follow later. The cleanup mechanism and acceptable delay remain open. [S3 lifecycle documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/troubleshoot-lifecycle.html) illustrates why asynchronous cleanup can lag expiration; this is supporting context, not a storage-technology selection.

For a download already in progress at expiration, the owner prefers allowing it to finish, but considers this a soft requirement dependent on implementation and code complexity. Defer the decision until the expected implementation is clearer; a prototype is an option for resolving it, not an approved experiment plan.

The owner decided that the source video becomes eligible for cleanup once the converted result is available for downloading. Source cleanup eligibility is therefore independent of the result's seven-day default retention period. Source videos from failed conversions must instead remain available for diagnosis and reproduction under the policy below. Actual source deletion timing and retention after cancellation remain open.

## Failed-source diagnostic retention

The owner confirmed a separately configurable diagnostic retention policy for source videos from failed conversions, defaulting to 60 days from recorded conversion failure, with deadlines preserved across restarts. The explicit deletion procedure and the decision whether to add or defer a deletion API are deferred until storage selection.

Agent guidance for the later deletion design: removal should preserve the failure history and leave source availability accurately represented. The procedure depends on the selected storage and metadata design. A deletion API does not inherently require user accounts in the already accepted local, shared-access environment; its scope and access policy are separate decisions.

Logs have a confirmed independently configurable age for deletion eligibility. The owner's proposed default is approximately two months; the agent recommends 60 days from log entry timestamps, pending confirmation. Actual cleanup granularity depends on the chosen logging technology. [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) calls for an explicit retention period for logs; it does not prescribe this project's default duration.

The phrase "diagnostic record" referred to the failed outcome and circumstances already required to be stored with a job, as distinct from chronological diagnostic logs. The owner confirmed that failure information is part of job information and shares the job's retention policy. It does not establish a separate component, storage representation, or retention policy. Example fields can be explored later without treating them as an agreed schema.

The owner requires long-term retention of complete job history in v1 to preserve the option of future analytics and statistics. The purpose includes observing product evolution and popularity, input/output format usage, and video sizes, potentially informing scaling, worker optimization, extensions, and popular conversion paths. These are examples, not an exhaustive set of questions or an agreed metadata schema. The owner does not want retention to depend on enumerating all future analytical uses now.

Analytics and aggregation implementation are deferred beyond v1. Aggregation is not universally preferable: it can reduce storage and simplify reporting, while retaining detailed history preserves the ability to ask questions involving recorded details not included in earlier summaries. No aggregate-only retention architecture is selected. Fields, sizing, and retention implementation remain open. Job-history retention includes failure information and is independent of video-file and log retention. [Microsoft's data-lifecycle guidance](https://learn.microsoft.com/en-us/azure/well-architected/cost-optimization/optimize-data-costs) ties retention to business requirements; [Google Analytics retention documentation](https://support.google.com/analytics/answer/7667196?hl=en-au) illustrates the distinction between event-level retention and aggregate reports.

The owner accepted configurable job-history retention with no automatic expiration by default for the local v1, plus an optional finite retention period for finished jobs. The policy covers failure information together with the rest of job information; active jobs are excluded from age-based history deletion. An arbitrary ten-year cutoff currently has no established business or operational basis. No automatic expiration preserves detailed history while analytics are deferred; history size and job volume can inform a later finite policy. The configuration representation, finite-retention start time, cleanup mechanism, and treatment of existing history after configuration changes remain open. Independent video-file and log retention policies are unchanged.

## Stage-duration and transfer limits

The owner confirmed no application-defined maximum source-file size for local v1. The rationale is the owner-operated, local-only environment and avoiding an arbitrary cap before representative workload sizes are known. This does not promise unlimited resources. An explicit size limit would provide a predictable per-upload boundary, but would not bound aggregate disk use or storage needed for converted results and temporary files. The owner separately confirmed no application-defined waiting-conversion count limit and retryable disk-full upload failures under the abandonment policy. Other resource-exhaustion details and concurrent-transfer limits remain open. Revisit the size policy when workload evidence or broader caller access warrants it.

No application-defined size limit does not mean that default hosting limits disappear. Review the selected upload path and hosting stack at setup so their effective limits match the agreed API behavior: [Kestrel has request-body limits](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/options?view=aspnetcore-10.0), and [ASP.NET Core upload handling](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0) can introduce form-file limits and buffering. No transfer encoding or implementation mechanism is selected by this recommendation.

The owner accepted a configurable maximum elapsed execution time per conversion attempt, separate from queue waiting and HTTP request lifetime. On timeout, stop conversion execution and record the failure and diagnostics without automatic retry. The default will be chosen later with the supported workload in mind; the owner explicitly wants unlimited execution considered as a possible default. No default is selected.

The owner confirmed a configurable waiting-inactivity timeout with a default of 24 hours for jobs awaiting an initial upload or interrupted-upload retry, ending in a terminal Abandoned state. This distinguishes incomplete submissions from conversion failures for status and history; it does not require a different state for every timeout cause. A later submission requires a new job rather than reopening the abandoned job.

The agreed timing starts the waiting period at job creation and starts a fresh period when an interrupted upload returns the job to waiting. Apply it only while waiting, not while an upload is actively transferring, conversion is queued/running, or a result is available. Polling does not extend the period, and a recorded waiting deadline survives server restarts. The 24-hour default allows an overnight retry window in the local learning environment without leaving forgotten jobs open indefinitely; it is a starting policy rather than an industry-prescribed value. It does not cap total job lifetime or replace active-transfer safeguards. Retain terminal job history under the existing policy; physical cleanup of partial files and exact state representation remain separate decisions.

The owner confirmed exposing the server-calculated abandonment deadline in job status while awaiting an initial upload or retry. Use an absolute timestamp so clients can display a deadline or countdown without duplicating the server's duration, reset, or configuration rules. The deadline is for upload waiting, not active transfer duration; polling does not extend it. A displayed value can become stale, so upload admission still checks authoritative server state. Field naming, wire serialization, and whether the field is absent, null, or historical outside the upload-waiting stage remain open.

The owner deferred the decision on v1 upload/download timeout safeguards until technology-stack selection, so implementation complexity can inform the decision. These safeguards are neither included nor excluded yet. Transfer policies remain agent proposals: distinguish maximum total duration from lack of progress or an unacceptably low transfer rate. Prefer progress/rate safeguards for uploads and downloads, with total-duration caps considered against supported file sizes and expected throughput. A timed-out upload ends that transfer attempt; a timed-out download should not change a successfully converted job into a failed conversion. These active-transfer safeguards are distinct from the confirmed waiting-inactivity policy. The owner selected no queue-wait expiration: waiting for conversion does not abandon a job, while the existing pre-upload abandonment, conversion-attempt timeout, and result-expiration policies remain separate.

Server-side transfer duration can be measured, but completing a server response does not prove the client saved the file. [ASP.NET Core request-timeout middleware](https://learn.microsoft.com/en-us/aspnet/core/performance/timeouts) and [Kestrel transfer-rate controls](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/options?view=aspnetcore-10.0) provide relevant mechanisms; actual enforcement depends on the selected hosting and protocols. Timeout cancellation signals must be handled; terminating the wait for a subprocess does not itself terminate its work. Implementation choices and numeric defaults remain open.

## Measurement and topology limits

For a stored-file flow, measure each bulk-transfer leg: client upload, worker input read, worker output publication, and client download. Also measure queue wait and conversion. Transfer can dominate total turnaround; distinguish result-ready time from time until download completes. Some stages may overlap if formats and processing allow it.

Benchmark job concurrency together with encoder threading: one conversion may already use multiple cores. CPU quotas can cause periodic throttling and affect short-request tail latency. Interpret latency alongside resource usage, throttling, disk/network contention, queue age, completion time, and errors.

Several containers on one host share CPU, memory, storage bandwidth, and a failure domain. Additional replicas model more capacity only within real host headroom. A single-host lab can exercise real protocols but cannot demonstrate independent host failures, disks, or multi-host bandwidth. Record topology and resource budgets alongside results. The owner selected their own computer as the v1 host; deployment tooling and resource budgets remain open. Rented or managed infrastructure, if considered later, would change operator effort, cost, transfer latency, and network dependencies.
